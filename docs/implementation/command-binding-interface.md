# 交易命令与持久意图的绑定

执行内核的 `OrderRequest` 保存资金预算和授权版本；交易所请求还包含标的、方向、价格、类型、有效方式及产品参数。两部分通过必填的 `command_digest: [u8; 32]` 绑定。摘要来自完整命令的规范编码，不能由网关在发送时从可变配置补齐字段。

## 内核与日志

`OrderRequest.command_digest` 参与请求相等性、提交收据核对和恢复。全零摘要表示缺失，预留与恢复均拒绝。内核保留固定大小摘要，不把变长命令放进逐单状态数组。

业务日志使用 schema 2。`PreparedIntent` 在原有键 0–13 后增加键 14，值为恰好 32 字节的命令摘要；其他事件的字段布局不变，信封、业务摘要和逻辑链的版本域统一使用 2。最长事件从 201 字节增至 236 字节。解码只校验编码文法，零摘要的业务拒绝由执行层负责。

schema 1 缺少命令绑定信息，不能通过补一个默认摘要升级成可发送订单。schema 2 解码器和业务日志 bootstrap 均拒绝 schema 1；原有测试样本另行保留，用来检查这个边界。物理 WAL 记录格式不变。

## 命令对象

交易所无关的命令类型提供受控构造、规范编码、解码及摘要。编码包含完整的业务参数和解释这些参数所需的标的版本。相同意图改变任一实际发送参数，必须得到不同摘要并触发请求冲突。

命令对象按摘要写入不可变存储，完成同步后才能用于授权和业务日志提交。恢复时读取原始对象，检查摘要、规范编码和请求身份；缺失或不一致时保持冻结。不可变对象应进入恢复依赖清单，副本才能检查完整性。

恢复清单使用依赖种类 13 表示完整命令。原有种类 1 仍是日志业务摘要的原像；种类 13 的内容摘要必须等于该意图的 `command_digest`。经过完整存储校验的 `VerifiedClosure` 暴露只读的命令依赖摘要，业务日志在首次提交、幂等提交和恢复时都核对它。清单允许不含种类 13，以读取既有对象格式；schema 2 业务意图不接受这种闭包。

## 发送协调

网络适配器接受由上述命令构造的不可变请求。等待连接、握手或可写期间不持有可跨等待复用的发送授权。每次首次接受应用字节前，执行所有者重新检查当前授权、租约和截止时间。

TLS 或其他输出缓冲区接受应用字节后，订单进入结果未知状态；随后发生断线或响应丢失，不得以换连接或换协议的方式重发。只有明确的未接受字节结果经业务日志持久记录后，才能释放对应预留。

## 验证顺序

先检查摘要对 CBOR 往返、业务摘要、提交收据、冲突去重和重启恢复的影响，再接入命令对象与实际网络适配器。网络测试使用真实 socket 驱动同一传输代码，覆盖等待期间失效、部分接受、响应丢失和重复回报。形式化模型分别对应命令绑定与首次发送的状态迁移。
