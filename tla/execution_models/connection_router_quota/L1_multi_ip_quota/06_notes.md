# Review notes

1. **Exact `can_afford` == `allow` equivalence under duplicate `RateLimitId`s and full rings**: When a single `spends` slice contains multiple entries targeting the same `RollingWindow`, the first spend pushes (or coalesces into) the tail entry at `now_ns`, so every subsequent spend on that same window in the same call is guaranteed to coalesce (`prior_units > 0`). Tracking `prior_units` per window in `RateLimiter::can_afford` (`crates/tickwire-quota/src/rate_limiter.rs:720-769`, `1338-1367`) keeps `ok`, `Exhausted.used`, and `Exhausted.retry_after_ns` bit-identical to `allow`.
2. **Action-class isolation (`Order` vs. `Cancel` vs. `Request`)**: Exhausting account `ORDER` fixed windows (`10s` / `1m` / `1d`) blocks only `Place` (and order-counting `Modify`), while `Cancel` (`SymCancel + IpWeight`) and `QueryDesk` recovery reads (`IpWeight` only) remain unobstructed (`CancelAndQueryIsolatedFromOrderCap`).
3. **Per-IP HTTP `429` failover vs. account-wide HTTP `418` freeze**: `note_ip_cooldown` (`crates/tickwire-quota/src/rate_limiter.rs:1117-1145`) scopes backoff strictly to the rate-limited `IpKey` so `pick_pool_slot_filtered` + `can_afford_quota_on_ip` seamlessly routes traffic onto healthy sibling source IPs (`PerIpCooldownIsolation`), whereas `freeze_account` (`418` ban) halts outbound quota admission across every IP on that account.
