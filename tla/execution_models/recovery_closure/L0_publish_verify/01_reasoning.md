# L0 抽象与状态

`cache[key]` 是当前能读取的固定文件内容；`disk[key]` 是已完成文件和目录同步的内容边界。两者使用具体 key/value 见证，不把“verified”布尔值当作持久事实。每个 root 有独立对象键和 manifest 键，两个 root 竞争同一个 binding 键；可观察冲突会保留原内容。

对象内容/schema/DAG/hash 解析以 `check` 的成功/失败出口抽象；shape 错误在开始拒绝，输入覆盖失败可发生在对象同步之后。字节解析、必需种类 1～12、可选种类 13～15 的配对规则、真实输入链和长度限制由 Rust 回归验证，模型不证明 SHA-256 无碰撞或策略采集端没有遗漏输入。

文件同步前的临时内容尚不可由固定 key 读取，因此临时写入/文件同步阶段不改变 cache。rename 后先改变 cache。一次目录同步成功会使整个目录中已 rename 且已完成文件同步的 cache 内容进入 disk，包含此前同步失败留下的其他 key；已有相同文件也再次经过文件和目录同步。多次操作失败后可以累积多个 cache 与 disk 不同的脏键。Survivors 为每个脏键独立选择旧 disk 或当前 cache 的全部组合；崩溃从中任选，已同步键始终保留。目录同步返回错误也允许这些存活组合，其他阶段的错误不推进 disk。目录本身先创建/同步，再同步父目录后才能开始闭包操作；失败后重开必须重复父目录同步。

每个同步调用成功后源码才继续下一步。Publish 遍历对象，再核对完整输入边界，最后同步 manifest/binding；Verify 先读并比较精确 binding/manifest，再走同样的重同步序列。issued 是已交付能力的历史见证，不是会因崩溃消失的局部变量。永久 pin 使所有已交付内容保持可达。

## 独立审阅修正

risk_core 指出初版仅以整份 disk/cache 表示崩溃结果，遗漏多个 rename 后目录同步失败所累积的部分存活组合。此修正来自源码与故障模型审阅，未出现先由 TLC 找到的实现反例。修正前文件与日志保存在 `pre-review/`；当前三组配置保持原容量，只扩大故障选择，不缩减动作或故障次数。

## 源码同步范围

从原锁定源码到当前源码，FileBlobStore 没有变化；publish/verify 仍在逐对象验证与同步后同步 manifest，再同步 binding，最后返回能力。新增摘要从已通过检查的 manifest 描述符读取，不新增 I/O、共享状态或提前返回。形状检查新增拒绝条件由既有 RejectShape 出口承接；该抽象只覆盖拒绝不授能力，不证明具体配对条件写得正确。

本次源码审查保留以上持久化抽象，TLC 转移公式和配置原样沿用。账户基线/历史摘要与每次准入之间的语义绑定由账户恢复接口、Rust 回归及其独立模型承担。
