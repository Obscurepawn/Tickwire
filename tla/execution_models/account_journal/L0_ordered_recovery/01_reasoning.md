# 抽象依据

`files` 表示基线、bootstrap 和物理日志创建结果的当前可见内容：0 为不存在，1 为不完整，2 为完整。`stable` 只记录已完成同步的状态。基线与 bootstrap 的独占创建、写入、文件同步和目录同步分别建模；只有前一文件完成后才建立下一文件。物理日志创建内部的 segment/manifest 细节合并为接口完成结果；其“完整可见”已经包含 manifest 临时文件同步后 rename，随后目录同步才使创建调用成功。恢复先重新打开 FileBackend，完成根目录与父目录同步，因此先前可见且已同步内容的目录项也会完成持久化。模型中的 physical 文件不表示真实单文件布局，未覆盖 segment/manifest 事务的全部微步。

`cache` 是完整封口批次中的记录序列，`disk` 是已同步序列，`tail` 表示末尾还有不完整批次。单次 append 只有一条记录，公开 `visible/history` 在同步成功后一起更新。失败封闭当前对象，完整尾批可能在恢复中保留。崩溃可留下未同步完整尾或不完整尾；所有已同步记录保留。恢复先检查物理批的 writer 非零且不回退，再核对 required 精确前缀，再修剪末尾并同步，最后才检查业务结构、调用闭包核验和重放账户。

每个历史摘要用有序的完整记录序列表示，在无碰撞前提下对应 `HistoryFrontier` 的滚动链。每个模型行同时携带物理 writer 和规范业务 payload；writer 不是业务编码新增字段。历史链另行绑定 writer 与日志序号。Admit 的 writer 必须等于其原意图代次，因此该类记录的闭包比对没有增加接口未提供的身份信息。闭包绑定记录与它之前的精确前缀；没有将前缀摘要展开成日志字节，也没有从 BlobStore 补回丢失记录。模型的可信 verifier 比较记录和前缀，缺失、错配或 I/O 失败均拒绝；它不发布缺失依赖。

创建后 append 并不自行验证账户计算或历史闭包。故模型允许记录包含错误的 AdmissionImage、错误的 Aborted 命令摘要，或者未保存闭包：追加收据仍只是字节持久化结果；恢复会在相应阶段拒绝。不能把“追加成功”作为风险批准的不变量。

恢复先完整遍历全部记录并检查连续序号、身份、writer 单调和 Admit 唯一性，再从空历史逐条执行 callback-before-advance。全部闭包通过后才重放账户。有限账户的账本序号与日志序号分开：重复 Aborted 增加日志长度，但不重复释放或增加账户序号。Admit image 的序号和 1 单位预留均按重放状态比对。返回账户始终冻结，恢复日志拒绝所有 Admit，包括旧意图重试。

给定配置的记录数和崩溃次数均有限，不通过 TLC 的状态约束剪掉超限后继。错误输入种子只在初始状态出现；没有提供事后任意改写成功提交记录的动作。文件内容和元数据的撕裂以可见/不完整/同步完成状态表示，具体字节错误继续由 Rust 协议测试验证。

首次可运行模型遗漏了 `FileStore::open` 的目录重同步，TLC 因而找到已可见 manifest 在重开后仍标作未同步的路径。逐行核对 `store.rs:44-62` 后补入该完成点；`04_evidence/model-open-omission.log` 保留原始反例。这是模型遗漏，没有据此修改源码或提出源码缺陷。

错误输入种子中的 writer=0 与物理代次回退由物理层先拒绝；`seq` 则表示业务信封的序号，物理 Record.seq 在本模型中始终是所在位置，故业务序号不一致由后续结构检查拒绝。这保留了物理校验早于截尾的实际顺序。
