# Coupled retention, management headroom, and prefix compaction

`Account`, `AccountGateway`, and `AccountJournal` bound resident state with active-protected monotonic retention windows (`now_mono_ns >= retired_at + Window`) rather than unconditional LRU eviction. An order in `Account` becomes retirable (`Account::is_order_retirable`) only when `!unknown`, no amendment targeting the order is in flight (`!aborted && !confirmed && rejected.is_none()`), and either `aborted` holds or `terminal && fees_closed && remaining() == 0` (`terminal_cumulative == Some(filled)`). Even after an order retires, `Account::evict_expired` retains the order, its `IntentKey` admission, and all associated `FactKey` entries until both `retired_mono_ns + Window <= now` and `facts_for_order_expired` hold, and `AccountGateway::evict_retired_entries` derives `completed_mono_ns` from `max(last_mono_ns, evaluated_at, intent_retired_mono_ns)` so gateway and reducer entries age out together.

Order-creating admissions (`New`) are capped at `MaxOrders`, whereas non-increasing management commands (`Cancel`, `Query`) draw from an independent `MaxMgmt` (`MAX_MANAGEMENT_ADMISSIONS`) pool. While queued on the outbound wire (`pending_send != 0`), `AccountGateway::submit` clears `retired_mono_ns` (`set_management_retired(key, None)`) so an in-flight management frame cannot be reclaimed mid-send. Once `apply_report(SendState::Flushed)` or `abort` completes the wire frame, the gateway stamps `retired_mono_ns` and `completed_mono_ns`, making the retired management entry immediately eligible for eager victim reclamation (`reclaim_one_retired_management_entry` / `reclaim_one_retired_management_admission`) when `MaxMgmt` fills before `Window` elapses—even if all `MaxOrders` slots are pinned by live resting orders.

Every durable transition appends to `AccountJournal`, advancing the rolling `HistoryFrontier` (`frontier_pos`) and 1-based record sequence `evicted_prefix + records.len() + 1`. When `records.len() + 1 >= MaxRecords` (`maybe_compact_journal`) or `compact_before(keep, MaxRecords / 2)` runs explicitly, prefix records are drained into `evicted_prefix`; any `Admit` record in `keep` (`Account` or `AccountGateway` admission keys) transitions from `AdmissionSlot::InRecords` to `AdmissionSlot::Retained` while preserving its `AdmissionOrigin`, whereas stale retained entries outside `keep` are purged.

Ghost specification observers (`ghost_orders`, `ghost_retire_at`, `admit_count`, `fact_first_at`, `trade_book_count`, `total_appends`) are never read by transition guards: `RetryDuplicateIntent` and `DuplicateTradeFill` execute the live table lookups (`gw_status`/`acct_adm` and `facts`) and increment `admit_count` or `trade_book_count` if an in-window key were ever missing, making `ActiveNeverEvicted`, `WindowDedupPreserved`, `ManagementNeverStarved`, and `FrontierContinuity` non-tautological. Outbound `New` and management commands follow Tickwire's monotonic per-strategy `intent_id` order (`strategy_sequence_floors`). The primary configuration (`NumOrders = 2, MaxOrders = 1, NumMgmt = 3, MaxMgmt = 2, Window = 2, MaxTime = 3, MaxRecords = 4`) checks multi-tick retention windows (`Window = 2`) and multi-candidate management victim reclamation (`MaxMgmt = 2`), while the burst configuration (`NumOrders = 3, MaxOrders = 2, NumMgmt = 1, MaxMgmt = 1, Window = 1, MaxTime = 2, MaxRecords = 4`) checks three competing `New` orders against a two-slot order pool alongside repeated journal prefix compactions.
