# Ownership, reservation, and bounds

`DialBaton` coordinates one session owner thread (`Idle`, `Ready`) and one `"tw-dialer"` worker thread (`Wanted`, `Dialing`) around a single staged `DialedLink` slot (`product: TimedSpinLock<Option<DialedLink>>`), with `Stopped` permanently terminal. `"tw-dialer"` leases a candidate address from `IpPool`, preferring an unused spare peer via `replace_with_unused` on reconnect and evicting failed zero-lease peers on `note_syn(peer, None)` only when at least one peer remains (`len > 1`). If the session owner calls `reset()` or `stop()` while `"tw-dialer"` is mid-handshake or delivering, `"tw-dialer"` observes `state != Dialing` (or `deliver_ready == false`), closes its private `ActiveAttempt`, and releases the `IpPool` lease without touching `DialBaton.product`.

`AsyncRestQuerier` bridges a hot-path producer/consumer and the `"tw-rest-query"` worker across two lock-free `SpscRing` queues (`task_queue` and `reply_queue`) of equal `Capacity`. Before popping a task from `task_queue`, the worker enforces `waiting.len() + usize::from(inflight.is_some()) + shared.reply_queue.len() < config.capacity`. Consequently, every task admitted into `waiting` or `inflight` holds an implicit reservation in `reply_queue`; `post_reply` appends unconditionally without a capacity guard, so TLC directly falsifies `ReplySlotReservation` if any completion or expiry path could ever exceed `Capacity` while `ConsumerDequeue` stalls indefinitely.

`sync_counted_send` latches `counted_send` and increments `query_count` only after the underlying `Connection` reports `accepted_bytes > 0` or `SendState::Flushed`. Unbuildable requests (`RestStatus::NotBuilt`), pre-send waiting deadline expirations (`RestStatus::Expired`), and zero-byte transport failures (`NoBytes` / pre-accept `SendFail`) leave `query_count` unchanged (`0` on the initial attempt). Post-accept `5xx` responses and transport errors retry with positive monotonic backoff while `can_retry` (`(max_query_count == 0 || query_count < max_query_count) && (end_mono_ns == 0 || next_send_ns < end_mono_ns)`) holds, whereas `2xx` and `4xx` responses post terminal replies immediately.

The primary configuration (`Capacity = 1, TaskCount = 2, MaxQueryCount = 2, MaxDialGen = 2, MaxTime = 2`) pits two tasks (one buildable with deadline, one unbuildable) against a single-slot ring across two reconnect generations and two candidate IPs. The scaling configuration (`Capacity = 2, TaskCount = 3, MaxQueryCount = 0, MaxDialGen = 1, MaxTime = 2`) exercises three tasks competing for a two-slot ring under unbounded count (`max_query_count == 0`) bounded purely by monotonic request deadlines. Deadlock checking is disabled because `OwnerStop`, exhausted time `MaxTime`, and drained tasks are legitimate terminal states.
