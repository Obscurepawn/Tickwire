# Durable order and restart

The sole mutable Local owner calls file installation before journal record. The physical journal appends one sealed batch per business step and returns its sequence. The logical ledger advances only after that successful append. The model splits these state changes to expose a lost receipt after persistence. A process stop can also occur between individual completed file installs. Reopening replays the sealed prefix and checks current files against the last recorded version or the exact next pending rendered version.

Each revision in this model uniquely identifies the immutable render, its prepared operation and the runtime witness. This quotient preserves equality, order and single-owner restart behavior; it cannot detect hash collisions, projected field omissions or two conflicting proposals naming the same revision. The scope and the physical file identities are fixed. Filesystem operations are represented after a completed sync. Faults inside file replacement and partial WAL writes belong to the storage layer. Crashes discard unreturned status and the in-flight runtime argument. Historical retries return the receipt sequence for an already recorded step. A preflight rejection changes only the observed API result.
