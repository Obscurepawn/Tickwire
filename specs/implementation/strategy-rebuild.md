# Schema 4 rebuild from a declared input window

Use schema 4 when a strategy declares the market and account observations it needs to initialize. Host first captures that exact window without running strategy code. After the window is sealed, the coordinator approves the operation. The same child runs the new factory on the captured inputs, syncs the resulting history and continues on its existing market and account subscriptions. The old version must separately demonstrate its rollback method. [Full-replay alternative](strategy-replay.md) · [Release and authority](strategy-handover.md)

## Window and action contract

`Plans` binds the operation's complete ordered membership and each target instance, generation, clock, executable, factory, state schema, parameters and model. A `Contract` declares streams, market classes, known levels, minimum distinct observations, logical time span and record/byte budgets. `Inputs` carries actual market checkpoints, the complete canonical account baseline and records, and the observed order of warm inputs. Requiring an unobserved historical ordering across independent sources is unsupported.

The first action contract requires complete Admit command evidence for every admitted economic action belonging to that logical strategy. The SDK checks the original action keys and exact commands and decodes real business checkpoints to prove that the actions remain consumed. Unknown, abort or terminal order state never resets those actions. Unlisted new admissions, duplicates, missing evidence or callback attempts to output commands fail the rebuild. An unknown market level cannot satisfy a request for a known zero. Warm observations count distinct applied records per class.

`CaptureOnly` seeds a private market and account replica from actual checkpoints at the start, with an empty warm list. The seed, record times and MD boot must use the same local monotonic clock domain (`clock_domain=1`). Each push verifies the candidate record, scopes, sequence, clock, action set and remaining window budget before publishing it. A bad input leaves the previous valid window intact. This capture mode accepts market application, observation markers and account records. It refuses configuration, models, user timers and unrelated external input. `finish` requires a nonempty current window, declared span and all coverage minima. Its seal binds both endpoint cursors, the complete input row chain and account digest.

## Capture, installation and rollback

| Phase | Wire operation and evidence |
| --- | --- |
| Capture | `registered --capture-only` establishes authenticated MD JOIN and an execution-owned report channel. The real PID is registered before admission. There is no intent lane or user factory. Seed at the exact initial account position, then retain subsequent warm records. |
| Seal | Report opcodes 41/42, kind 8, bind capture ID, exact bootstrap and contract, absolute deadline and requested final account position. Sequence zero is valid. Host stops sending later reports. The worker waits for the exact position and sufficient warmth or rejects an already-passed cut. It syncs attempt, window and receipt before replying. |
| Install | Kind 9 binds the approved operation/member, complete plans/manifest, captured facts, target bootstrap and expiry. Its expected sequence is the warm row count and its cut digest is the WindowSeal. Refusals use flags 18 and status 1–3. A duplicate identical request reuses the receipt. A different request cannot run the factory again. |
| Rollback | The old binary independently restores C after exact replay, or a separately approved old contract rebuilds from its own window. `--rebuild-rollback` verifies the job, syncs a one-use attempt, executes the real old factory with outputs closed, verifies the cut, then syncs anchor, transcript, checkpoint and final marker. Host observes the independent PID and its successful exit. |
| Bind rollback | Kind 10 binds the verified installation, independent probe completion, full dependencies and deadline. The target verifies and syncs these without running the old factory. It persists the rollback root and issues a new v4 READY. The coordinator requires this root before final handover. |

The capture attempt uses a new 0700 directory. It syncs `ATTEMPT.json`, the contract, seed, complete inputs and seal, then `CAPTURE_WINDOW.json`. Host rereads the worker's stored bootstrap and seal request and compares them byte for byte with those sent. `VerifiedWindow` replays the fixed SDK observer over the real input sequence and checks the complete result. Host checks the actual report applied/released cursor, same live registry child, session and deadline after disk I/O. Repeated requests can return only the original result. An invalid or expired owner terminates and reaps its child. Cooperative stop requires actual MD detach and report QUIESCE followed by successful exit. Child death alone cannot prove detach. [Capture run](../evidence/20261028/capture-runtime.json)

App enables this mode with `HostConfig.capture` and a private absolute publication directory. `objects.json` indexes sorted unique CAS items. `forward-files.json` and `rollback-files.json` map roles to absolute deployment files verified against the manifest. The approved owner supplies `capture-seal.json` with schema 1, capture ID and exact account position. Host checks it at 10 ms intervals. Only a verified window can become the basis for signed plans. The installation binds the actual config and recovery-template files the target will use. Host releases its exclusive CAS writer before requesting kind 9 so the worker can own it during installation.

## Continuing with the same engine

`execute_running` calls the matched factory once, rebuilds isolated account and market replicas and runs the actual warm callbacks with command output closed. Its in-memory `RunningCandidate` holds that exact application, timers, RNG, input chain and cut. Persistence syncs eight content objects and a completion object, then an empty genesis and its warm delta commit. `Live::from_rebuilt` verifies the live replica sets and syncs HEAD. The worker connects the authenticated intent channel from the same PID, keeps the existing report and MD cursors and consumes the next actual record at C+1. It does not call begin again, reset sequence or redeliver the account baseline. Ring exhaustion, loss of continuity or any sync failure keeps the gate closed.

A v4 seal can carry the installation digest before rollback finishes. Management transfer, replica recovery and use as a later old source require the independent rollback root as well. Recovery verifies the full path from capture completion through attempt, seed, actual inputs, receipt, bootstrap, request, installation and probe. It checks the original seed against the warm-free start and recomputes the window input chain. The recovery reader never executes user code or reopens historical paths. Typed objects are limited to 16 MiB, opaque dependencies to 64 MiB, the complete graph to 512 objects and 256 MiB, and nested old-version graphs to depth 16. The probe attempt ID hashes the domain `tickwire.rebuild.probe.v1`, canonical install request and installation root so a new revision/member cannot inherit someone else's attempt.

## Account responsibility and coordinator recovery

The actual account baseline and window records must be an exact prefix of the owner's history. A new unlisted Admit after the window requires a newly captured and approved operation. During Prepare both old and new forwarding gates close. Unsent commands stop. Potentially sent actions and unknown orders keep their reservations. Acknowledgements, fills and fees after C enter as real reports. App checks the current account WAL, ledger, order digest, actual READY, freshness and frozen state after each cold step and before it signs Prepared. An expired account evidence interval causes a durable Halt even with time remaining on the operation.

The member WAL syncs the original Prepare and fixed roots, warm completion, installation, independent rollback completion and signed `RebuildPrepared` in order. An uncertain write never advances in-memory authority. Schema 4 permits a missing initial business READY in `MemberAuthority.readiness`, but always requires the actual installed READY. Schemas 1–3 retain their original requirement and encoding. The coordinator records each member's seven fixed roots, actual cursors, observed READY, gate/state versions, challenge and deadline. Commit requires all applicable members and the exact durable `RebuildAdoption`. It appends a single StrategyHandover to the account WAL. Release verifies all committed receipts and the signed group release. The target opens only after actual retirement of its predecessor. After restart, fresh Query and `RebuildObserved` recover history. An explicit resume and new Prepare refresh current readiness. The factory, install and probe never rerun merely to refresh a receipt.

The Linux release scenario used actual V1/V2 workers, a signed coordinator and a loopback exchange. The new worker kept its capture PID, the old-version probe exited successfully, the successor preserved the C10→D285 hash prefix and the old active worker exited. Mirror and successor matched all 12 account records, including the late 0.001 BTC fill and terminal fees. A development build reached Prepared after the account evidence expired and was denied.
