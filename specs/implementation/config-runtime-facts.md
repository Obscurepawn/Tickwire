# Signed observations of configuration targets

`tickwire_config_service::runtime_facts` verifies signed host reports covering every process in the *committed baseline*. `RuntimeTrust` ties the underlying evidence-trust digest to a named issuer, host and explicit process set. Each host has exactly one source. Process scopes must be unique across hosts, with no wildcards or overlaps. The issuer must hold the `RuntimeTargets` kind. The verifier authenticates the Ed25519 envelope and actual artifact bytes for `runtime_targets`. An HTTP caller cannot grant an issuer this scope. [Verifier](../../crates/tickwire-config-service/src/runtime_facts.rs)

Inputs are the actual head's candidate and revision, plus projections computed from that same baseline. Each host contributes one strict schema 1 document carrying cluster, namespace, host, boot, source epoch and sequence, observation time and the processes it observed. Their union must equal the full base process set, including unchanged and retiring processes. Two fragments from one host cannot be combined across epochs. A new successor needs separate qualification.

For each process the verifier checks role, assigned host, artifact build hash, instance, process/host boots, positive Linux PID, execution and locator generations, slot, current revision, global and projection hashes, projection policy revision and applied event sequence. UUIDs and hashes cannot be all zero. Version and sequence fields are canonical decimal strings from 1 through 2⁶³−1. Instances, process boots and slots are individually unique. Strict parsing rejects extra or duplicate fields, invalid numbers and trailing content.

Observation must precede or equal issuance, which must precede or equal service time. Effective expiry is the earlier of envelope expiry and observation time plus a configured age of 1–60,000 ms. The result is already invalid at that instant. Limits are 256 host documents, 4,096 processes, 4 MiB per document and 16 MiB total. Only successful full verification constructs the private `RuntimeTargets` value. Its digest binds the baseline, revision, startup scope and signed source materials independently of reference ordering.

Tests cover actual signatures, incomplete and duplicate sets, cross-host scope, swapped base projections, incorrect roles and builds, mixed epochs, future/expired data and capacities. A fresh operation must recheck the current head, trust, provider and time. A production provider, durable anti-rollback source watermarks, the current resource registry head and runtime/file application receipts are separate requirements.
