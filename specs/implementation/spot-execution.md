# Bybit and OKX Spot Execution

`tickwire-spot-execution` and `tickwire-spot-runner` implement native cash spot order execution, private-stream ingestion, operator inspection tooling, cold stateless exchange bootstrap, and bracketed REST recovery for Bybit V5 and OKX V5. When a strategy submits a `CanonicalCommand`, `AccountGateway` reserves cash on `Account`, commits the recovery closure and `Admit` record to the configured `StorageMode` (`InMemory` default stateless mode, `MmapAsync` preallocated `MAP_SHARED` + background `fdatasync`, or `LocalDurable` synchronous `fsync`), and re-verifies its live trading `Gate` immediately before the first plaintext byte enters TLS. Outbound orders carry 32-character `[0-9a-z]` `SelfDescribingClientId` identifiers (`"t1"` + 30-char Base32) so cold Pod restarts reconstruct strategy ownership, intent sequence floors, and deterministic internal UUIDs directly from Bybit and OKX `openOrders` REST snapshots. One spot encoder instance binds a fixed `SpotVenue`, `Environment`, logical account, API credential scope, and calibrated exchange UTC clock, translating admitted commands into signed native HTTP requests without mutating client order identity.

## Execution Model and Supported Operations

| Operation | Outbound Request | Evidence Established by Reply or Stream |
| --- | --- | --- |
| Create order | Cash `LIMIT` or `MARKET` order denominated in base units carrying the original `ClientId`. | Venue request acknowledgement only; asynchronous order-status updates and individual trade executions follow separately. |
| Modify order | In-place price/quantity cash `LIMIT` amendment (`POST /v5/order/amend` on Bybit V5, `POST /api/v5/trade/amend-order` on OKX V5) targeting a resting order by `orderId`/`ordId` or `orderLinkId`/`clOrdId` (with optional `reqId` on OKX). | Emits `VenueEventBody::Modified` (supporting venue-clamped `px`/`sz` on HTTP replies and `order.spot`/`orders` streams) or `VenueEventBody::ModifyRejected` with classified `TerminalReason` without freezing `Account`; ambiguous transport disconnects isolate `DoubtReason::AmendAmbiguous` on `QueryDesk`. |
| Cancel order | Single target order scoped to the bound account and native instrument. | Venue cancellation-request acknowledgement; the order can still fill in an execution race until terminal status and trade coverage settle. |
| Query order | Single order lookup on its native instrument symbol. | Matching order ID and instrument establish an observed lifecycle snapshot; a cache miss or interrupted connection leaves the outcome unknown. |
| Book / project a fill | Authenticated execution row carrying native trade ID, side, quantity, price, signed fee, and fee currency; optional volatile `ProjectedFill` from advancing `cumExecQty`/`accFillSz` on `order.spot`/`orders` when `projected_fill_enabled == true`. | `Account` books settled cash, inventory, and per-trade fee once on trade fills; `ProjectedFill` projects early incremental fills using exact fixed-point `CumulativeQuote`, `AveragePrice`, or `LimitFallback` without mutating settled cash or double-counting when trade executions arrive. |

For every inbound fill, the private-input owner supplies the original `IntentKey`, internal order ID, account `Scope`, source `connection_epoch`, and durable input-stream sequence to `record_fill`. `record_fill` loads the original admitted `CanonicalCommand` from the same gateway journal, validates native IDs, instrument, and side, and persists the normalized `CanonicalEvent` through `AccountGateway::record_ingress_event`. OKX fills apply the per-execution fee directly; any unrecognized fee currency or unsupported Bybit regional fee halts booking while preserving the authenticated raw wire envelope in the private input log for deterministic replay.

## Operator Inspection (`tickwire-spot-observe`)

`tickwire-spot-observe` inspects live or test Bybit and OKX accounts over TLS using read-only API credentials supplied via `TICKWIRE_SPOT_KEY` and `TICKWIRE_SPOT_SECRET` (plus `TICKWIRE_SPOT_PASSPHRASE` on OKX), or via mounted secret files using the corresponding `*_FILE` environment variables (specify exactly one source per credential):

```sh
cargo build --locked -p tickwire-spot-execution --bin tickwire-spot-observe
target/debug/tickwire-spot-observe bybit test open-orders BTCUSDT
target/debug/tickwire-spot-observe okx test balance
```

* **Point queries (`open-orders`, `balance`, `order`, `fills`)**: `order SYMBOL CLIENT_ID` looks up a single order within the venue's retention window, and `fills SYMBOL [CURSOR]` reads one page of executions. Each invocation samples the public exchange clock, signs a private `GET`, and validates TLS certificates on both connections. Output is structured JSON containing HTTP status, venue response code, selected fields, sample timestamp, and any continuation cursor, bounded to a **2 MiB** HTTP body per page (`balance` inspects the Bybit Unified wallet or OKX trading account). Transport errors, malformed payloads, or venue rejections exit with a nonzero status.
* **Bounded range scan (`scan EXPECTED_UID START_UTC_MS`)**: Given a numeric UID and a `START_UTC_MS` within the past **3 days**, `scan` verifies native UID identity before the first page and again after the final page, paginating wallet balances, standard spot open orders across instruments, and spot fills up to the sampled exchange timestamp (checking Bybit execution time or OKX transaction time per row). Each collection permits at most **128 pages** and **8 MiB** of selected row data under a **120-second** clock-sample expiry; duplicate IDs, repeated cursors, or out-of-window rows fail the scan. Because pages are read across multiple instants—and OKX algo orders plus non-order transfers lie outside this CLI scan—the output reports `fresh_risk_qualified: false` and never substitutes for a live trading grant.
* **Live stream monitor (`watch EXPECTED_UID SECONDS`)**: Observes private WebSocket traffic for **1–60 seconds** after verifying `EXPECTED_UID` over REST with the same key, emitting one JSON line per event (`order.spot`, `execution.spot`, and `wallet` on Bybit; SPOT `orders` and trading-account `account` on OKX, where ordinary-tier accounts receive per-fill execution fields on `orders`). Each run tracks subscription acknowledgements, heartbeats, and its own message count, terminating immediately on venue control errors or unexpected products. Rust callers embed the same parser through `PrivateFeed::on_text` and `Batch::records`.

## Core Invariants and Account Recovery

Reconnecting a private WebSocket cannot by itself certify account state: neither Bybit's `wallet` stream nor OKX's `orders` stream delivers an opening portfolio snapshot; Bybit reuses execution sequence numbers across symbols; OKX can repeat order frames or report a filled market order with a zero last-fill quantity; and identical pre-gap and post-gap wallet totals can mask an intervening order placement/cancellation or offsetting cash transfers.

`tickwire-spot-runner` resolves these ambiguities through bracketed dual-scan reconciliation:

* **Continuous private journaling across `StorageMode` profiles**: One runner owns one dedicated Bybit or OKX cash account, authenticates `expected_uid` on every connection, and journals session boundaries alongside raw channel frames before applying transitions. `StreamConfig` and `Capture` ([`src/private/capture.rs`](../../crates/tickwire-spot-execution/src/private/capture.rs)) honor `StorageMode`: `StorageMode::InMemory` uses `Journal<InMemoryStore>` + `InMemoryBlobStore` with zero disk directories or syscalls and bounded ring/window descriptor and frame-blob trimming past `max_descriptors` so long-running streams never halt at `1,000,000` frames; `StorageMode::MmapAsync` uses `Journal<MmapAsyncStore>` + `AsyncFileBlobStore`; and `StorageMode::LocalDurable` (the default when `storage_mode` is not overridden) enforces owner-only `0o077` directory checks with `Journal<FileStore>` + `FileBlobStore`. Contiguous updates for known open orders and accounted trades advance an existing grant, and matching `(trade_id, economics)` pairs book once across WebSocket, REST, and replay.
* **Background pre-warmed reconnects and pooled multi-IP HTTP/1.1 routing (`LiveNetwork`, `RestSession`, `OrderRouter`, `VenueRateLimiter`)**: `LiveNetwork` and `SocketConnection` ([`src/network.rs`](../../crates/tickwire-spot-execution/src/network.rs)) optionally integrate `tickwire_transport::dialer::{Dialer, DialBaton}` so background TCP+TLS reconnects pre-establish replacement `Connection`s off the `AccountRunner` hot path while preserving deadline-bounded direct dialing when no `Dialer` is attached. When `RestSession::with_connection_pool` / `enable_connection_pool` ([`src/session.rs`](../../crates/tickwire-spot-execution/src/session.rs)) activates pooled execution (`execution_pool_size > 1` or `!local_ips.is_empty()`), up to `MAX_ORDER_CONNECTIONS` (`16`) exclusive HTTP/1.1 keep-alive slots (`SendSlot::Exclusive`, `max_inflight == 1` per socket) bind across `1..=N` local source IPs via `LiveNetwork::attach_pool_slot` / `create_pool_baton`. `OrderRouter` round-robins across ready slots until each accrues 8 microsecond RTT samples (`SampleKind::Order`), then routes to the lowest-EWMA ready slot while staying sticky on `last_conn_id` inside the `9/8` (`12.5%`) hysteresis band. When a `VenueRateLimiter` (`VenuePreset::BybitSpot` or `VenuePreset::OkxSpot`) is attached, `RestSession::submit` derives a deterministic non-zero `symbol_rate_key(instrument_id)` (auto-registering per-symbol rolling windows on OKX) and filters candidate slots by per-IP and per-action quota (`allow_place` on `New`, `allow_modify(..., counts_as_order: true)` on `Modify`, `allow_cancel` on `Cancel`, `allow_query` on `Query`—keeping `CANCEL` and `REQUEST` windows strictly isolated from `ORDER` caps on both Bybit `20/1s` and OKX `60/2s` symbol / `1000/2s` account, and debiting tokens only **after** `AccountGateway` admission succeeds so local `CrossesBook`, `InsufficientAsset`, `TooManyPendingActions`, or `NoChange` refusals burn zero tokens); local quota or IP-cooldown exhaustion returns `SessionError::RateLimited(RateReject)` **before** `AccountGateway::submit_on_slot` reserves funds or writes to `AccountJournal`.
* **Immediate gate closure vs. per-order `QueryDesk`, `Modify` outcomes, `ProjectedFill`, and per-IP `429` isolation**: In default whole-account mode (`per_order_doubt_isolation == false`, `per_order_query_desk: false`, unpooled), any stream gap, wallet balance message, terminal order status, or unaccounted frame revokes permission to admit new risk while the private reader continues capturing incoming messages. When per-order isolation or pooled execution is enabled (`RestSession::with_per_order_doubt_isolation(true)` / `AccountRunner::with_per_order_query_desk` / `per_order_query_desk: true`), `classify_issue` partitions responses into `DeterministicReject` (records `VenueEventBody::Rejected` with classified `TerminalReason` on `New`, or `VenueEventBody::ModifyRejected` rolling back `pending_modify` and keeping the resting order open on `Modify`, without freezing), `NotFound`, `Ambiguous` (isolates only the affected order in `DoubtReason`—including `DoubtReason::AmendAmbiguous` / `AskKind::Amend` for `Modify`—and enqueues it in `QueryDesk` while sibling orders continue trading on healthy keep-alive slots or `Dialer`-replaced sockets), and Category B `AccountHazard` (HTTP `401`/`403`/`418` or invalid API key / permission errors, which freeze `Account` immediately). Terminal Bybit (`rejectReason`, `cancelType`, `smpType`, e.g., `CancelBySmp`, `EC_PostOnlyWillTakeLiquidity`, `170131`, `170213`) and OKX (`cancelSource`, `cancelSourceReason`, `sCode`, e.g., `51008`, `51019`, `51400`, STP `"32"`) order updates classify exact `TerminalReason` values via `classify_spot_venue_reason` (`AccountRunner::order_terminal_reason`). When `AccountRunner::set_projected_fill(true)` is enabled, advancing cumulative fills on Bybit `order.spot` (`cumExecQty`, `cumExecValue`, `avgPrice`) and OKX `orders` (`accFillSz`, `avgPx`) emit `ProjectedFill` ahead of execution frames and converge deterministically with deduplicated trade fills. In pooled multi-IP mode with a `VenueRateLimiter`, HTTP `429` or venue rate-limit error codes (Bybit `10006`, OKX `50011`, `is_venue_rate_limit_code`) record a per-IP cooldown (`note_ip_cooldown` using `Retry-After` or a `1s` default) on the affected slot's `local_ip` and isolate only that slot's in-flight intent into `QueryDesk` without freezing `Account`, allowing subsequent orders to fail over immediately onto healthy sibling source IPs; mid-request socket `EOF`, decode errors, or send deadlines call `drop_broken_slot_isolated` on that slot alone while sibling slots continue serving orders. Likewise, when a private WebSocket `orders` frame arrives ahead of its corresponding fill (`cum > filled`), only that order enters `DoubtReason::FillCatchup` (`AskKind::Trades`) rather than freezing the entire account; wallet `balance` frames, stream gaps, and cumulative regressions still trigger full dual-scan reconciliation.
* **Off-hot-path `PerOrderQueryDriver` (`AsyncRestQuerier`)**: [`query_desk_driver.rs`](../../crates/tickwire-spot-runner/src/query_desk_driver.rs) drives `OrderStatus` (checking Bybit `realtime` then `history` before concluding absence, and OKX `/api/v5/trade/order`) and `OrderTrades` (Bybit `/v5/execution/list`, OKX `/api/v5/trade/fills`) off the hot path via `AsyncRestQuerier`, and harvests background `Dialer` pool reconnects via `poll_pool_dials`. When resolving `DoubtReason::AmendAmbiguous` (`AskKind::Amend`), `PerOrderQueryDriver` compares queried `(qty/sz, price/px)` against resting pre-modify terms: if `(qty, price)` changed on the venue, it emits `VenueEventBody::Modified` with the actual exchange `(qty, price)`; if unchanged or terminal without modification, it emits `VenueEventBody::ModifyRejected` so `pending_modify` rolls back cleanly and `AmendAmbiguous` clears. Before dispatching due status or trade asks, `PerOrderQueryDriver::step` gates against `VenueRateLimiter` `REQUEST` quota (isolated from `ORDER` and `CANCEL` windows) and optional `with_allow_query` callbacks: if `REQUEST` capacity is momentarily full, the ask stays queued via `on_not_sent` without incrementing `issued_query_count`. Unconfirmed orders remain locked in `PlaceAmbiguous` throughout `not_found_grace_ns` before `CloseUncreated` releases cash, fills apply via `record_fill` prior to terminal `OrderObservation` and `FeesReconciled`, `CancelRejectedStillOpen` with zero remaining pending cancels clears `CancelAmbiguous` while keeping open principal locked, and `max_query_count` exhaustion escalates to `freeze_cash()`.
* **Bracketed two-scan proof**: An independent recovery worker collects **two** authenticated REST scans starting `60 seconds` prior to the last covered venue timestamp (clamped at `baseline_utc_ms`). Reactivation succeeds only if the private stream cursor and `AccountJournal` position remained stationary across the bracket, both scans agree on order terms, fills, fees, and spendable/locked cash, and zero unexplained orders or transfer bills appear (even if offsetting flows leave net cash unchanged). Both scan transcripts are archived to disk before synchronizing `RecoveryRecord::Reactivated`, and crash recovery re-verifies the archived pair against the private journal before acquiring a fresh grant.
* **Side-effect-free idle-window hot-path cache warming (`RestSession`, `AccountRunner`)**: When configured via `with_warmup_interval_ns` / `set_warmup_interval_ns` (`warmup_interval_ns: u64`, `0` = disabled by default), `RestSession` and `AccountRunner` track outbound submissions, synchronous replies, private cash frames, and public quote activity via `record_activity(now_ns)` and execute `maybe_warm_hot_path(now_ns)` strictly when no order is in flight and the session has been idle for `>= warmup_interval_ns`. Each dry-run iteration (1) decodes a venue-representative Bybit or OKX BBO quote JSON frame into stack ticks and lots, (2) evaluates exact `Fixed` candidate notional/fee bounds and `StpBook::self_cross` against read-only `&Account` and a startup-cloned scratch `Account`, (3) signs and frames a synthetic Bybit (`X-BAPI-SIGN` HMAC-SHA256 hex) or OKX (`OK-ACCESS-SIGN` HMAC-SHA256 Base64) `POST` order HTTP/1.1 request into a preallocated `[u8; 2048]` scratch slice using a synthetic signing key, and (4) drives `TlsLoopbackWarmer` roundtrip encryption/decryption and parses the echoed HTTP `200 OK` JSON acknowledgement—leaving live `Account` balances/orders, `AccountJournal` sequences, `Origins`, `OrderRouter` EWMA scores/inflight counts, `VenueRateLimiter` token buckets, and live `Connection` TLS nonces 100% untouched.

## Run an account

Provision one exclusive Linux state directory and one dedicated API credential set per trading account, initialized from a canonical `baseline` CBOR file whose cash balances, fee schedule, and instrument catalog match the venue at `baseline_utc_ms`. `reconcile` requires read-only account permission; `live` additionally requires spot order permission.

```sh
cargo build --locked -p tickwire-spot-runner
target/debug/tickwire-spot-runner reconcile /absolute/account.json
```

`reconcile` verifies remote state, persists the reactivation proof, and prints `spot_account_reconciled` once. Before starting a subsequent process against the same state directory, increment `policy.writer_epoch` beyond the highest durable writer epoch and update strategy producer configs to match that epoch:

```sh
target/debug/tickwire-spot-runner live /absolute/account.json
```

`live` holds the private WebSocket open and services configured strategy queues (when `policy` is `Stopped` with empty strategy queues and market sources, `live` continuously reconciles the account). Creating `stop_file` triggers an orderly shutdown. A private WebSocket reconnect keeps the active `writer_epoch`. In default whole-account mode, if the outbound order connection drops while an admitted request's transmission outcome is uncertain, `live` halts so a restart under a newly approved `writer_epoch` resolves the outstanding order by `ClientId`; when `per_order_query_desk: true` (or per-order session isolation) is active, single-order socket drops isolate only the in-flight order in `QueryDesk` and install a pre-warmed replacement `Connection` from `Dialer` without halting the process, Bybit empty `/v5/order/realtime` replies chain `/v5/order/history` before treating an order as missing, and previously confirmed orders returning not-found isolate `DoubtReason::FillCatchup` to fetch per-order trades before closing.

| Deployment Field | Meaning and Invariant |
| --- | --- |
| `baseline`, `baseline_utc_ms`, `expected_uid` | Absolute path to canonical account baseline CBOR, UTC millisecond start of venue history covered by that baseline, and decimal native UID string—permanently bound to `state_directory`. |
| `state_directory`, `account_stream`, `private_stream`, `initial_writer_epoch` | Absolute storage root, two distinct 16-byte WAL stream UUIDs, and genesis writer epoch. Keep the account WAL, private input WAL, and recovery object store together. |
| `per_order_query_desk` | Optional boolean (`false` by default). Enables per-order `RestSession` doubt isolation, `QueryDesk`, and `PerOrderQueryDriver` (`AsyncRestQuerier` + `Dialer` execution reconnects) in `live` trading mode. |
| `execution_pool_size`, `local_ips` | Optional connection-pool slot count (`1..=16`) and unique non-unspecified local source IPs. When `execution_pool_size > 1` or `!local_ips.is_empty()`, `live` enables pooled `RestSession` routing (`RouterConfig::default()`), attaches `DialBaton` slots cycling across `local_ips`, and installs a `VenueRateLimiter` (`BybitSpot` or `OkxSpot`). |
| `warmup_interval_ns` | Optional `u64` nanosecond idle threshold (`0` by default = disabled). When nonzero, `live` seeds `AccountRunner::record_activity` from the live monotonic clock at startup (`last_activity_ns == 0 && last_warm_ns == 0`) and runs side-effect-free `AccountRunner::maybe_warm_hot_path` during quiescent reactor turns after `>= warmup_interval_ns` of inactivity. |
| `policy` | Runtime policy pinning `Scope` (including `test` or `production` environment), boot clock domain, catalog digest, `writer_epoch`, `OwnerLease`, and strategy grants. |
| `market_sources`, `strategies` | Authenticated shared-memory market subscriptions and per-strategy file queues (each naming a nonzero `logical_strategy_id`, exclusive absolute `directory`, and `first_sequence`). |
| `stop_file` | Absolute path to the shutdown sentinel file, which must be absent at startup. |

Immediately prior to writing the first plaintext order byte, the gateway samples the private reader's durable cursor, connection status, and last heartbeat deadline; any detected disconnect closes the send gate immediately. Socket bytes still queued in the kernel become visible on the reader's next poll and are drained into the account thread in batches of up to **64 records**.

## Performance and Cost

Per-order submission formats decimals and IDs into owned strings, serializes the JSON body or query string into an HTTP buffer, computes a single-pass HMAC-SHA256 signature (lowercase hex on Bybit, Base64 on OKX) using an amortized calibrated clock sample, copies wire bytes into a bounded `PreparedSend`, clones `Account` for candidate risk admission, synchronizes the recovery closure and `Admit` record to the WAL, and evaluates the first-byte `Gate`. Order status updates and trade fills each incur separate journal writes; storage `fsync` latency, TLS readiness, and single-slot queue wait should be profiled as distinct intervals.

Background REST pagination, discovery, and TLS reads execute on the dedicated recovery worker thread while the trading thread drives the order connection's TLS handshake ahead of the first command. An unexpired grant can continue serving orders while a background renewal scan runs (discarding the scan if the account journal or private cursor advances in the meantime), though replaying the archived scan pair, verifying ledger parity, and synchronizing `Reactivated` execute on the account owner thread. End-to-end live exchange latency on this path has not yet been benchmarked.
