# Linux file backend for the configuration journal

`tickwire_config_fs::JournalStore` consumes a private directory store under an exclusive lock and implements the physical journal's `Store` interface. It scans, creates and syncs segments through the directory FD. The physical journal owns batch framing, hash chains, consecutive record numbers and the required durable frontier. [Linux backend](../../crates/tickwire-config-fs/src/linux/journal.rs) · [Physical journal](journal.md)

The defaults allow 128 segments, 16 MiB per segment and 256 MiB total, with a bounded directory scan. Only 20-digit decimal segment IDs are accepted. Unknown files, links, wrong owners, unexpected modes and files on a different device fail validation. The backend records inode, length and nanosecond modification/status times and checks those facts on later reads, appends and syncs. This binds the bytes validated during recovery to the file actually synced.

Creation syncs both file and directory. Append writes at the observed offset and retains that FD through sync. An uncertain write, truncate or sync poisons the store. Recovery truncates the last segment first and syncs the entire verified prefix in order. While earlier segments sync, it retains the dirty last-segment FD. Manifest replacement compares the currently observed bytes with the previous expected digest *before* accepting an exact retry. An out-of-band replacement therefore fails even if it contains precisely the proposed new bytes.

The recorded Linux phase ran 22 config-fs tests, 21 physical-journal tests and all-targets Clippy for config-fs. Regression tests reproduced manifest drift, mismatched read/sync inodes and the multi-segment sync ordering issue. Real children were killed after a partial write, before sync, after sync and after receipt. Recovery checked complete batches and subsequent append continuity. SIGKILL leaves the kernel running. The tests did not simulate machine power loss. [Local configuration records](config-local-journal.md)
