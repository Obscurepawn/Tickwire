# 配置 journal 的物理文件后端

`tickwire-config-fs::JournalStore` 消费一个已经持有独占锁的私有 `Store`，实现 `tickwire_journal::store::Store`。它沿目录 FD 打开、扫描、创建和同步分段；批次帧、hash chain、连续序号及 required frontier 仍由物理 journal 处理。

默认容量为 128 段、单段 16 MiB、分段总计 256 MiB。目录项数也有上限。分段名只接受二十位十进制编号；未知文件、链接、异常属主/模式和跨设备文件被拒绝。读取保留实际 inode、长度及纳秒级修改/状态时间，后续读取、追加或同步都核对先前观察，防止把旧文件的读取结果与新文件的同步结果拼接。

创建分段完成文件和目录同步。追加在实际 offset 上写入，并持有同一 FD 到同步结束；写入、截断或同步不确定失败后关闭该 Store。恢复先截断最后一段，再按序同步完整前缀：同步前段时保留最后一段的 dirty FD，轮到最后一段才清除 dirty。

manifest 安装先比较当前字节摘要与后端此前观察的摘要，再允许精确重复。即使外部替换的文件恰好等于本次准备发布的字节，也报告漂移。普通配置文件允许相同内容重试的行为保持原样；journal 使用独立的严格旧值检查入口。

Linux 结果覆盖 config-fs 22 项及物理 journal 21 项测试，并通过 config-fs all-targets Clippy。其中三项回归先复现了 manifest 漂移误接受、读取与同步 inode 脱离、多段恢复同步顺序冲突，再验证修复。真实子进程在部分写入、同步前、同步后和返回收据后被 SIGKILL，恢复检查完整批次、可信旧前缀和后续连续追加。SIGKILL 保留运行中的内核，不作为机器断电测试。

隔离测试工作区由两个 crate 组成，Cargo 将原锁文件中的 223 个包裁剪为实际所需的 25 个；保留包的版本、checksum 和解析后的依赖关系均相同。前后锁文件、输入摘要和最终源码归档分别保留。

该后端提供物理同步证据；ConfigPrepared、运行时 ConfigApply 和配置物化 agent 的业务状态继续由上层实现。
