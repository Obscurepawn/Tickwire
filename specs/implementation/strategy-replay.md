# Ordered strategy input and schema 3 handover

A schema 3 handover restores an old binary and its original configuration at checkpoint S, replays to the actual cut C, migrates state, applies the new configuration and installs the result. `TWINP002` preserves input order, callback times, timers, RNG and output digests. Historical callbacks have no `IntentWriter`. During live operation the SDK syncs callback results, inputs and the completed checkpoint before it publishes a command. [Worker handover](strategy-handover.md)

`tickwire-release::replay` verifies the object graph. SDK runs real factory callbacks and writes durable files. Host pins the executable, authenticates the child and checks actual cursors. App verifies the complete account prefix. Every stage binds the same source S, signed Prepare and complete operation/member. `CommittedHistory` validates the full chain across schema 1 complete prefixes and schema 2 delta commits. Only actual replay by the old factory can demonstrate that generic business state matches its saved endpoint.

## Market transitions during replay

`MarketTransition` is one structural input. It contains a nonzero operation ID and approved-plan digest, the entire previous cursor, the next stream key, baseline and activation sequences, and the actual `TWSB0001` JOIN baseline. The catch-up list stores each 512-byte record, payload and application time in order. Applying this input swaps the market replica and cursor without invoking user callbacks or emitting effects. The new client takes over only after the transition, checkpoint, commit and HEAD are durable.

The old client's applied waterline must agree with its replica and QUIESCE cursor. The successor retains the required topic, channel, catalog version, producer and clock identity, advances ring/feed generations and satisfies predecessor/cutover/first-sequence continuity. Existing instrument IDs and versions survive. SDK verifies the snapshot, applies all catch-up records and compares the complete replica and actual activated cursor with the live client. Older checkpoints lack a catalog hash, so trusted plan admission checks catalog continuity. An unsupported old executable rejects the new input variant. An oversized typed baseline or catch-up segment is rejected before commit.

The stream's `cursor_basis` determines its digest. Omitted or zero uses the original complete Input hash. Basis 1 hashes the canonical `MarketApplied` for the last actual catch-up record at the activation sequence, including the producer's ingress timestamp. Two readers of the same producer record can therefore compare cursors even when their JOIN resources or local times differ. The full transition and local times still enter the merged input chain. An unknown basis, a snapshot that skips C, a missing transition, an incorrect old cursor or a reused successor stream fails. For basis 1 with no catch-up, the new client stays paused until it applies a genuine record or its deadline expires.

Report opcodes 41/42 carry kind 6 Arm and kind 7 Commit. Both use `expected_sequence=0` and `expected_cut_digest=approval_digest`. The typed control request is limited to 2 MiB. Arm verifies the actual old connection, successor template, replay support and lifecycle exclusion, then syncs the approval. MD waits for all approved readers to be Armed before revoking old subscriptions. The worker records the actual applied cursor after it releases borrows, retries the whole QUIESCED frame under backpressure and pauses callbacks. An ordinary unapproved QUIESCE retains retirement semantics.

Commit drives a bounded authenticated `PendingJoin`, checks the cut, persists `MarketTransition` and HEAD, appends the full row and endpoint to retained recovery history, then exchanges consumers and resumes callbacks. Request retries return the original result only for identical content. A pre-Arm rejection uses opcode 42, flags 18, with Unsupported=1, Busy=2 or Invalid=3. Errors after revocation keep the worker closed. App syncs its control decision before Commit. MD syncs effective state before opening JOIN. Overall completion uses App's effective receipt. ## Installing at the cut

1. At startup the target restores/migrates S and stores `replay_restore_digest`. After the old instance stops forwarding intents, Prepare takes the actual C and starts the pinned old executable with `--source-replay`.
2. Host issues the authenticated installation. SDK verifies and syncs the result, including the full commit chain through C and subsequent retained inputs. The target records `replay_installation_digest`. Inputs with different bytes cannot substitute for one another merely because they reach the same book.
3. A separately identified rollback probe exercises the C checkpoint after ConfigApply. Host observes its actual successful exit. The target syncs `replay_rollback_digest` and issues a new READY. HandoverSeal v3 retains all three roots. The static factory registration binds its ID, raw configuration, revision and executable. Unknown factory IDs, cross-clock conversion and configuration/model changes in the retained Shadow interval are refused.
4. Execution syncs objects before its lifecycle state. Uncertain sync leaves authority closed. Idempotent completed retries require the same authenticated session. Commit needs the coordinator's exact `ReplayAdoption`, a current READY, matching account records, order capability and gate. After restart `ReplayObserved` exposes the historical installation to a new Query. All domains must reply and an explicit resume must refresh Prepare before Commit can proceed.

Typed replay objects retain their 16 MiB limits. Opaque dependencies, including a complete old ELF, can be up to 64 MiB each within a 256 MiB closure. The running Linux process verifies its own `/proc/self/exe`. Recovery independently requires the approved Binary object. Actions consumed by the old generation stay consumed after migration and configuration changes.

## Regression history

Early Linux runs exposed four distinct problems. Rewriting the entire input prefix on each flush caused backlog. Writing an install object as a private `.bin` made it invisible to the normal CAS reader. Loading a 34-object closure for every READY consumed the original 30-second handover budget. Finally, checking only the last incremental commit compared its local start with C incorrectly. The fixes append deltas rooted in the preceding commit, use `ReportWriter::put_object`, reserve full closure checks for the final challenge-bound READY, and verify the entire bounded commit chain. The validated READY cache binds body, directory, child, session and expiry. Actual account and consumer evidence is checked at use.

The October 28 release run used real V1 and V2 counting workers. It replayed S=2 to C=10, installed, ran an independent rollback probe, committed, released, retired the old PID and processed a late fill. Padded ELFs of 16 MiB plus one byte passed another run at S=2, C=22. Both matched 12 account records at mirror and target and closed terminal fees under the original deadlines.
