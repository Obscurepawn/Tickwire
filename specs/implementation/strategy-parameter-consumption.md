# Verifying the parameters consumed by a strategy

`HostConfig.projection_parameters` connects an approved global `strategy.params` value to the configuration consumed by a particular running worker. The global projection revision and digest identify the deployment decision. The factory's private revision and original bytes identify the input used in the worker. App withholds the first queued intent until it verifies both identities at the worker's current checkpoint.

## Approved inputs

The optional binding names the complete projection file and `ObjectBinding`, its cluster, namespace, host and process, the parameter schema file and a bounded query deadline. It applies to the first launch of a registered worker with the checkpoint-query capability. Checks cover role, logical strategy, namespace, exact instance, local channel identities and executable digest. Omitting the binding preserves the original startup behavior. If launch resources or input scope are also constrained, all enabled checks must use the same complete projection and scope. [Startup binding](supervisor-process.md) · [Account and market inputs](strategy-input-consumption.md)

`tickwire_config::artifacts::validate_parameter_document(schema_bytes, expected_schema_hash, parameter_bytes)` verifies the raw SHA-256 named by `parameter_schema_ref`. The offline JSON Schema 2020-12 validator bounds regular expressions, rejects external references and accepts at most 1 MiB and 32 nesting levels for the schema. The private configuration comes from the absolute path, raw object digest and revision in the bootstrap's `FactoryBinding` and is limited to 2 MiB. Strict JSON rejects duplicate keys, floats, out-of-range integers, extra input and excessive depth. The top-level parameter object contains 1–256 properties with at most 16 nesting levels. App compares the canonical `Candidate` with the full approved value. Different whitespace or key order can match the projection while the factory still reads the original bytes.

## First-intent gate

The registered SDK hands the actual `VersionedBytes` to `Registration::configure`, verifies the factory readback and checks its replay registration after construction. The runtime records the resulting configuration in `RuntimeState`. A fresh Host query reads `RuntimeState.config` from the current merged checkpoint named by the verified input seal. An old startup checkpoint or an unrelated object with the same digest cannot answer that query. The source clock must match the query's logical clock domain and approved host boot. Host also samples the actual kernel boot identity independently. [Checkpoint query](runtime-observation.md)

App continues to drive market and account input while withholding queued intents. The internal query advances at most once every 10 ms, including while waiting for the account baseline or a busy Host. Its original absolute deadline is at most 30 seconds and is checked again after disk and kernel reads. Timeout or mismatched evidence closes the gate and reaps the managed worker. External queries cannot take or cancel this internal result. If input scope is also enabled, both checks share the same challenge, process and checkpoint and use the earlier deadline. Proofs become available together before intent delivery.

`AppStrategy::projection_parameters(target)` returns a `ParametersProof` for the exact logical strategy, instance and generation. The proof records one observation. Global runtime/file application and order authority have their own owners. Six recorded Linux process tests used an independent counting worker and an authenticated MD JOIN server in the test process. They covered optional compatibility, rejection before startup, current private configuration, changes in counting and minimum bid, and withholding intents through timeout.
