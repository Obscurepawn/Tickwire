# Native REST evidence for cash account recovery

An account scan binds an authenticated venue UID and environment to one trading wallet, its regular spot orders, individual fills and cash bills. Each call uses a fixed official HTTPS authority, bounded HTTP decoding and an exchange UTC clock sample. The scan starts and ends with an authenticated UID check. The local journal's logical account ID and the exchange UID may differ. The deployment binds them at genesis. ## Cash account coverage

| | Bybit V5 | OKX V5 |
| --- | --- | --- |
| Account profile | UTA 2.0 or 2.0 Pro, regular margin mode and spot borrowing switched off. Inspect all linear settlement currencies returned by the standard and pre-market instrument endpoints, plus inverse and options. Outstanding orders or positions in these three derivative categories stop recovery. | Spot account mode. Inspect pending spot algorithms, active spot grids and recurring-buy bots. Orders carrying a contingent leg stop recovery. |
| Wallet | For each returned currency require nonnegative cash, known spot locks, no borrowing and equity equal to wallet balance. Derive cash available as wallet balance less spot orders' locked quantity. | Require native available plus frozen to equal cash balance, and equity to equal cash. In verified spot mode an explicitly empty liability field is accepted alongside numeric zero. Nonzero debt and noncash encumbrances stop recovery. |
| Order coverage | Read account-wide spot open orders and order history. Follow every native cursor. The default order filter includes conditional spot orders, which the ordinary cash profile rejects. | Read all standard pending spot orders and order history. Follow the last order ID until an explicitly empty page, including after a short page. Spot conditional algorithms have separate endpoints. |
| Historical bounds | A scan start must be less than 24 hours before the sampled venue time. Fully canceled, rejected and deactivated orders have shorter retention than filled orders. | A scan start must be less than two hours before sampled venue time. Canceled orders with no fill have two-hour retention. History filters by order **creation** time. |
| Fill evidence | Execution ID, order ID, client ID, quantity, price, reported quote amount, execution time, signed fee and fee currency. A positive Bybit execution fee debits cash. Unsupported extra regional fees stop recovery. | Trade ID, bill ID, order ID, client ID, quantity, price, fill time and per-trade fee and currency. A signed negative native fee debits cash. Pagination and the native interval use bill ID and the processing timestamp `ts`. The account fill uses `fillTime`. |
| Cash activity | Paginate the authenticated transaction log. A trade bill must identify a returned managed fill. | Paginate trading-account bills and require corresponding spot trades. Currency transfers and unattributed balance changes, including offsetting movements, stop recovery. |

A known unresolved order is queried separately by instrument and client ID even when it predates the history window. Bybit falls back to its historical endpoint if realtime lookup returns no rows. A missing, ambiguous or mismatched result prevents recovery. A managed limit order must have the same execution terms (GTC, IOC, FOK or post-only) as its admitted command. The Bybit order row reports these in `timeInForce`. OKX encodes them in `ordType`. A new or cancel ACK provides no terminal order evidence. Use an exclusive trading account with no other order writers or products that can subsequently move cash. REST snapshots alone cannot exclude an external writer enabling a new bot after the scan. [Order and fill parsing](../../crates/tickwire-spot-execution/src/recovery/rows.rs) · [Account profile](../../crates/tickwire-spot-execution/src/recovery/profile.rs)

**Event contracts are outside the supported account profile.** Start both venues with a dedicated UID whose event orders and positions the operator has verified are empty, and keep event trading disabled or unused. Bybit restricts its event-order and event-position endpoints to Event Contract maker accounts. Its API key record describes the calling key’s permissions, and its UTA account info describes the margin profile. Neither documents an account-wide event exposure flag. An event transaction returned in the scanned window stops recovery. An older position can be absent from that window. On OKX, `acctLv=1` establishes spot account mode. The scan queries `instType=SPOT`; it does not inventory `EVENTS` orders or positions. Existing event contracts can settle cash later. [Bybit key info](https://bybit-exchange.github.io/docs/v5/user/apikey-info) · [Bybit account info](https://bybit-exchange.github.io/docs/v5/account/account-info) · [Bybit event orders](https://bybit-exchange.github.io/docs/v5/event/trade/open-order) · [Bybit event positions](https://bybit-exchange.github.io/docs/v5/event/trade/position) · [OKX event contract settlement](https://www.okx.com/en-us/help/how-to-trade-event-contracts-and-settlement-logic)

For Bybit spot, several cash-log rows may match one fill through its symbol, order ID and trade ID. Tickwire identifies each row by `(symbol, orderId, tradeId, currency, id)`. This accepts two currency legs carrying the same native log ID. Repeating the same composite key within or across pages stops recovery. Bybit labels `id` unique, but its example reuses one value for a linear settlement and a linear trade. The example makes no claim about ID reuse between spot currency legs. ## Recording and replay

The transcript retains each request path, HTTP status and response bytes. UID/config responses are reduced to their identity fields first, because Bybit's native response contains the API key. Replay reconstructs the request sequence and continuation tokens from the stored responses. It checks the window, profile, target order identities, asset totals, per-trade charges and cash bills again. Missing, duplicate or surplus pages and contradictory order snapshots cannot certify the account. The caller compares two scans with the same start, strictly increasing end times, equal economic fingerprints and a current private-stream cut. On restart the account journal rechecks the recorded pair and requires a new approved writer epoch. [Proof verification](../../crates/tickwire-spot-runner/src/reconcile/proof.rs)

Scanning runs on the recovery worker. Each HTTP read currently incurs DNS resolution, a new TCP/TLS connection, JSON decode and bounded buffering. The scanner keeps up to 512 responses, at most 2 MiB per native page, 12 MiB of retained raw responses and 24 MiB of serialized transcript. A standard order or fill list also has its own 128-page bound. Explicit local order lookups are capped at 128 per scan. Capacity, timeout, retention or rate-limit errors leave the account frozen. These bounds affect how many active orders and how much recent history one deployment can recover. [Recovery worker](../../crates/tickwire-spot-runner/src/live/scan.rs)

Run the parser and transcript regressions with `cargo test --locked -p tickwire-spot-execution --test recovery`. On Linux with glibc, a C compiler and Python 3, `cargo test --locked -p tickwire-spot-runner --test reconcile_process` also exercises the official REST and WebSocket names against a loopback TLS exchange using a per-process resolver. For each venue it reopens the journal, changes private connection epochs and submits one limit buy through the live gateway. The simulated exchange verifies the native signature and returns a fill with a fee. After disconnecting the private stream, each account must qualify again with the resulting inventory and cash.
