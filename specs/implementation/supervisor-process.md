# Managed Process Supervision, Executable Pinning, and Resource Enforcement

`tickwire-supervisor` and the Linux execution primitives in `tickwire-control-sys` bridge static deployment authorization and live operating-system processes and threads. When launching a managed worker, the supervisor snapshots the approved ELF image into a sealed kernel `memfd`, optionally locks and populates a preconfigured cgroup v2 leaf and CPU/NUMA envelope before `exec`, and retains an unreaped `Child` handle per registered instance. Retaining the direct child handle prevents PID reuse across authentication and runtime queries, ensuring that control handshakes and `/proc` observations bind to the exact process created by the launcher rather than an arbitrary local PID. Within each process—including market-data publishers, strategy workers, and unified ORS execution processes—`tickwire-control-sys` also provides audited thread-level CPU affinity (`CpuSet`, `pin_current_thread`, `current_thread_affinity`, `spawn_pinned_thread`) and cold-startup core isolation checks (`validate_cpu_isolation`) so higher-level crates retain `#![forbid(unsafe_code)]` with zero raw `libc::sched_setaffinity` calls outside `tickwire-control-sys`.

Process supervision owns main-binary freezing, child lifecycle tracking, credential/image correlation at connection acceptance, thread-level CPU mask enforcement, and kernel resource sampling. Adjacent layers retain their distinct responsibilities: dynamic linkers and shared libraries (including `$ORIGIN` search paths) remain host deployment dependencies; parent-allocated `memfd` images and shared-memory banks charge against the supervisor's memory budget rather than the worker's `memory.max`; and a live process or resource proof attests only to the sampled instant—subsequent releases, configuration transitions, and order-admission risk grants require their own independent evidence.

## State Model and Bounds

`Registry` is a single-owner process table keyed by 16-byte `instance` UUID. Each `Entry` pairs the live `Child`, its immutable `ExecutableImage`, an optional non-clonable `ResourceDomain`, the expected `Identity` and UID/GID, connection state, `last_control_epoch`, and cached `ExitStatus`. Non-Linux targets reject OS execution and affinity primitives with `UnsupportedPlatform`.

| Parameter or Resource | Enforced Bound / Representation |
| --- | --- |
| Registry capacity | `1..=4,096` managed instances (`Error::Capacity` outside range or when full) |
| `LaunchSpec` arguments & environment | Absolute executable and working directory paths; at most 128 arguments (`<= 16,384` bytes each, no NUL) and 128 environment entries (non-empty keys `<= 256` bytes without `=` or NUL; values `<= 65,536` bytes without NUL) |
| `ExecutableImage` | Regular executable ELF (`\x7fELF`, class 1 or 2, data 1 or 2, version 1; minimum 52 bytes for 32-bit or 64 bytes for 64-bit) up to 512 MiB; scripts (`#!`) and symlinks rejected |
| `ExecutableImage` seals | Mandatory `F_SEAL_WRITE \| F_SEAL_GROW \| F_SEAL_SHRINK \| F_SEAL_SEAL` (`0x0f`) plus `F_SEAL_EXEC` when supported; reopened `O_RDONLY \| O_CLOEXEC` with writable description closed prior to `exec` |
| `CpuSet` & kernel `Mask` | Non-empty, strictly ascending, duplicate-free CPU IDs in `0..=4,095` (`1..=4,096` CPUs, 512-byte / 4,096-bit stack `Mask`); `FromStr` parses Linux CPU list syntax (`"2"`, `"2,4-7,10"`) and `Display` emits canonical range lists (`Error::InvalidResources` when empty, `>= 4,096`, duplicated, malformed, or inverted) |
| `validate_cpu_isolation` | Every `Some(cpu)` in `hot_cpus` must satisfy `cpu < 4,096` (`Error::InvalidResources`), all `Some(cpu)` entries must be pairwise distinct across roles (`Error::ResourceConflict`), and `hot_cpus ∩ housekeeping_cpus == ∅` (`Error::ResourceConflict`) |
| `ResourceLimits` | `1..=4,096` strictly ascending CPU IDs in `0..=4,095`; single `numa_node` in `0..=31`; finite `memory_max` in `1 MiB..=2^53 - 1` bytes (`1,048,576..=9,007,199,254,740,991`) |
| Cgroup v2 leaf requirements | `cgroup.type == "domain\n"`, exact `cpuset.cpus.effective`, single `cpuset.mems.effective`, exact `memory.max`, `memory.swap.max == 0`, zero descendants in `cgroup.stat`, and empty `cgroup.procs` / `cgroup.threads` |
| Kernel `/proc` read caps | `/proc/<pid>/stat` bounded at 8 KiB (`>= 50` post-`comm` fields); `/proc/<pid>/status` bounded at 64 KiB; cgroup control files bounded at 32 KiB; up to 4,096 threads in `/proc/<pid>/task` |
| `HostConfig.projection_launch` | Projection object `<= 4 MiB`; OS credential name map `<= 128` entries; active registered `strategy` role, trust profile `qualified_sdk`, and restart policy `never` |

## Core Invariants

* **Immutable execution from a sealed descriptor**: Opening a deployment pathname directly during `execve` would allow a concurrent rename, overwrite, or unlinking on disk to swap the bytes that actually start running. `ExecutableImage::open` instead opens the source with `O_NOFOLLOW | O_CLOEXEC | O_NONBLOCK`, copies at most the stat-sampled byte length into a `memfd` created with `MFD_CLOEXEC | MFD_ALLOW_SEALING | MFD_EXEC`, chmods it `0555`, applies immutable content seals, opens an independent `O_RDONLY | O_CLOEXEC` handle via `/proc/self/fd/<fd>`, and drops the writable handle so `execve` cannot fail with `ETXTBSY`. Only then does `Registry` stream the sealed `memfd` through SHA-256 and verify `Identity.build_hash`. Only `EINVAL` on `MFD_EXEC` or `F_SEAL_EXEC` falls back to older kernels lacking executable-seal flags; policy denials such as `EPERM` from `vm.memfd_noexec` abort startup immediately.
* **Program-path preservation across configuration callbacks**: `ExecutableImage::configured_command` points `Command` at `/proc/self/fd/<fd>` while preserving the original deployment path as `argv[0]`, and verifies after the caller's configuration closure runs that `Command::get_program()` still names that exact descriptor path. The qualified SDK independently verifies its own running image via `/proc/self/exe`.
* **PID-reuse and `exec`-replacement immunity**: `Registry::accept` requires an owned, unreaped child whose `SO_PEERCRED` (`pid`, `uid`, `gid`) matches the registered launch, rejects any `HELLO` carrying ancillary file descriptors, and checks both *before* `Session::accept` and *after* sending `WELCOME` (bookended by `try_wait` liveness checks) that `/proc/<pid>/exe` still shares the exact device, inode, byte length, and immutable seals of the retained `ExecutableImage`. If the child exits or `exec`s a different binary mid-handshake, the session is never published.
* **Async-signal-safe pre-exec placement**: `ResourceDomain::acquire` walks each absolute directory component with `O_DIRECTORY | O_NOFOLLOW | O_CLOEXEC`, verifies `cgroup2` filesystem magic, and takes a nonblocking exclusive inode lease (`DirectoryLease`) before validating controller settings and confirming empty `cgroup.procs` and `cgroup.threads`. Each lease permits at most one `spawn` attempt (`attempted = true`) and never mutates cgroup controller knobs. Rust's standard library applies target `uid`/`gid` changes before invoking the private `pre_exec` hook; inside the forked child, `Setup::run` performs only allocation-free `pread` comparisons against parent-snapshotted cgroup files, writes `"0"` to the pre-opened `cgroup.procs` descriptor (which Linux authorizes against both the opener's file credentials and the common ancestor of source and target cgroups), applies `sched_setaffinity(0, ...)` and reads back the exact 4,096-CPU mask to catch silent kernel clipping, and re-verifies cgroup settings before `exec`. Any mismatch aborts execution of the ELF.
* **Audited thread-level CPU pinning, read-back verification, and housekeeping core escape**: Linux `clone(2)` copies the calling thread's `sched_setaffinity` mask to newly spawned threads, so launching a process under `taskset` or pinning a main thread to a hot core causes naive `std::thread::spawn` background threads to inherit and contend for that hot core. Cold startup first calls `validate_cpu_isolation(hot_cpus, housekeeping_cpus)` to verify that every configured hot core is `< 4,096`, pairwise distinct across hot roles (for example `req_cpu != resp_cpu`), and disjoint from `housekeeping_cpus`. Hot threads bind via `pin_current_thread(&CpuSet)`, while cold background threads (dialers, REST query workers, control sockets, telemetry sinks) launch through `spawn_pinned_thread(name, affinity, f)`: when `affinity` is `Some(set)`, the child thread calls `pin_current_thread(set)` to escape the parent thread's hot-core `sched_setaffinity` mask onto `housekeeping_cpus` (whenever permitted by `cpuset.cpus.effective`) *before* executing `f()`, and when `affinity` is `None`, the child inherits the parent mask unchanged. Because Linux `sched_setaffinity(0, ...)` succeeds whenever at least one requested CPU is online and permitted by `cpuset.cpus.effective`—silently masking off offline or cgroup-excluded cores—`pin_current_thread` immediately calls `sched_getaffinity(0, ...)` (`current_thread_affinity` uses the same 512-byte mask read) and verifies exact equality with `cpus`, failing immediately rather than silently degrading.
* **Bracketed double-sampling for live observations**: `Registry::observe` is a cold verification path that checks child liveness, samples `/proc/<pid>/stat` (`start_ticks`), `/proc/<pid>/status` (requiring all four real, effective, saved, and filesystem UID slots and all four GID slots to match the expected credentials), `/proc/<pid>/exe` identity, and the nonzero kernel UUID in `/proc/sys/kernel/random/boot_id`, then resamples process state, image identity, and liveness afterward. `Registry::observe_resources` brackets `ResourceDomain::observe` between two full `Registry::observe` calls and two `/proc/<pid>/task` scans, verifying that `cgroup.procs` contains `[pid]`, `cgroup.threads` equals the stable sorted thread list, and every thread satisfies both the exact CPU affinity mask and the configured NUMA node.

## Operations and Failure Semantics

* **Cold-startup affinity validation and synchronous thread-pinning handshake**: `CpuSet::from_cpus`, `CpuSet::single`, and `CpuSet::from_str` reject empty sets, CPU IDs `>= 4,096`, duplicate CPU IDs, malformed tokens, and inverted ranges with `Error::InvalidResources`. `validate_cpu_isolation` rejects any hot CPU `>= 4,096` with `Error::InvalidResources` and rejects duplicate hot-role assignments or any overlap between `hot_cpus` and `housekeeping_cpus` with `Error::ResourceConflict`. In `pin_current_thread(cpus)`, a kernel syscall rejection returns `Error::System { operation: "set thread affinity", .. }`, a read-back syscall failure returns `Error::System { operation: "read thread affinity", .. }`, and any discrepancy between the requested `CpuSet` and the `sched_getaffinity(0, ...)` read-back mask returns `Error::InvalidResources`. In `spawn_pinned_thread(name, Some(set), f)`, interior NUL bytes in `name` return `Error::InvalidResources` before spawning; otherwise the spawned thread reports its `pin_current_thread(set)` outcome over a synchronous startup channel before running `f()`. If pinning fails, the spawned thread drops `f` without executing it, unwinds without invoking the panic hook, and is joined by `spawn_pinned_thread` before returning `Err(e)` synchronously to the caller.
* **Routine polling vs. cold attestation**: Hot supervision loops call `Registry::process(instance)` or `observe_exits()`, which issue only lightweight `try_wait()` checks without reading `/proc`. `ExitObservation` proves only that the directly supervised process exited; it does not prove that forked descendants or shared-memory mappings have detached. Reconnection after `disconnected(instance, epoch)` requires a strictly higher `control_epoch` and never renews trading authority.
* **Single-child termination and lease lifetime**: If post-`exec` resource verification fails inside `ResourceDomain::spawn`, or when `Registry::terminate` or `Drop` runs, the supervisor signals (`SIGKILL`) and reaps only its directly owned `Child`—it never writes to `cgroup.kill` or signals bare recovered PIDs. Exiting does not release the `ResourceDomain` lease on the `Registry` entry; when the `DirectoryLease` eventually drops, it explicitly unlocks the directory inode before closing its descriptor so a transient descriptor inherited across a concurrent `fork` cannot prolong the lock, and the next acquisition must again observe a genuinely empty cgroup leaf. Note that `memory.max` bounds kernel-charged pages (which may experience brief transient overages before reclaim), while exclusive physical core isolation, `mlock`, and cross-NUMA page migration remain host-level setup responsibilities.
* **Projected launch binding (`HostConfig.projection_launch`)**: Before spawning or connecting to workers, `App` validates all local bootstrap channel identities, executable SHA-256 digests, cluster/namespace/host/process/strategy bindings, role, OS credential mappings against actual kernel credentials, and worker CPU/NUMA/memory budgets against the projection. External workers must pass observation before `App` exposes their owner; local lazy workers (`prepare_start(now)`) wait for live market data, spawn the child, and complete live image and resource attestation before `LaunchBindingProof` is published or the first strategy intent is admitted. Any attestation failure terminates and reaps the managed child. Parameter and input-scope gates, when enabled, bind to the same projection identity under separate runtime proofs.

## Verification and References

```sh
cargo test --locked -p tickwire-supervisor -p tickwire-control-sys
cargo clippy --locked -p tickwire-supervisor -p tickwire-control-sys --all-targets -- -D warnings
```

The Linux test suite covers `memfd` ELF freezing, growing-source races during copy, post-`exec` image replacement detection, credential quartet mismatches, pre-exec CPU affinity and multithreaded inheritance, thread-level `CpuSet` isolation validation, kernel TID affinity escape from a `taskset`-pinned hot thread onto housekeeping CPUs verified via `/proc/self/task/<tid>/status` (`Cpus_allowed_list`), synchronous fail-before-closure pinning rejection, fake-cgroup rejection, and projected launch purpose validation. On the archived October Linux host, positive end-to-end cgroup v2 leaf tests remained unexecuted because the host environment did not delegate an empty writable leaf with `cpuset` and `memory` controllers enabled.
