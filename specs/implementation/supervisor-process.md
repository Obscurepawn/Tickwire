# Managed executable identity and process resources

The Linux supervisor launches the approved executable bytes and retains the child handle used to authenticate and observe that process. App can also require a specific CPU set, NUMA node and cgroup memory limit. An attested launch describes the sampled process and fields. A later release, resource change or order requires its own evidence.

## Executable and child

`ExecutableImage` opens the approved regular ELF once with `O_NOFOLLOW | O_NONBLOCK`, copies it within a size limit into a memfd, applies WRITE, GROW, SHRINK and SEAL seals, then checks the sealed image's SHA-256 against `Identity.build_hash`. A renamed, replaced or removed deployment path cannot change those bytes. The supervisor uses the fixed descriptor path for `Command` and checks that the configuration callback did not change the program. It retains the CLOEXEC descriptor per registry entry. Only `EINVAL` on optional kernel flags permits an older-kernel fallback. A policy denial such as `EPERM` closes startup. Non-Linux returns Unsupported. Dynamic loaders and libraries, including private libraries found through `$ORIGIN`, remain host deployment dependencies. Scripts are rejected.

`Registry::accept` checks the owned, live child before and after the handshake and compares device, inode, size and seals of its actual `/proc/<pid>/exe` with the approved image. Executing a different image under the same PID invalidates authentication. `Registry::observe` is a cold operation that checks kernel boot ID, start ticks, and all real, effective, saved and filesystem UID/GID values. It bounds each proc read and checks the same child and image on both sides of the sample. `LiveChildObservation` records approved identity, actual process and image, control epoch and start of the sample. The existing control epoch identifies the connection. A fresh challenge uses the observation protocol. Ordinary `process()` polls keep their lightweight exit check. [Process query](runtime-observation.md) · [Linux memfd policy](https://docs.kernel.org/userspace-api/mfd_noexec.html)

The SDK verifies its running image from `/proc/self/exe`. A complete historical Binary object remains a separate recovery dependency. Each entry retains its own main ELF in its owner's memory budget. [Image acceptance](../evidence/20261029/runtime-image-acceptance.json)

## Cgroup and CPU enforcement

The worker resource plan supplies the absolute cgroup path, memory limit, CPU set and NUMA nodes. The launcher validates the plan before spawning the worker.

`ResourceDomain::acquire` requires a preconfigured empty cgroup v2 domain leaf. `ResourceLimits` accepts 1–4,096 sorted unique CPU IDs between 0 and 4,095, one NUMA node between 0 and 31 and a finite memory limit of 1 MiB through 2⁵³−1 bytes. The supervisor opens each absolute path component with directory/no-follow semantics and checks cgroupfs. It takes an exclusive nonblocking inode lease before reading effective CPUs, the single effective memory node, exact `memory.max`, `memory.swap.max=0`, children and membership. The lease is cooperative. Deployment owns the hierarchy and controls outside writers. The supervisor does not reconfigure controllers.

A lease permits one launch attempt. Before the ELF executes, a private `pre_exec` hook writes `0` to the pinned `cgroup.procs`, sets affinity and reads back the exact mask. It uses prepared descriptors and fixed storage. Insufficient migration permissions, kernel clipping or any failure prevents this ELF from starting. Rust applies UID/GID changes before the hook. Linux also checks migration rights at the common ancestor of source and destination. After exec, failure of a later observation terminates and reaps the directly created child, which may already have run. No group-wide kill runs. [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html) · [Linux migration checks](https://github.com/torvalds/linux/blob/v6.18/kernel/cgroup/cgroup.c) · [CPU affinity](https://man7.org/linux/man-pages/man2/sched_setaffinity.2.html)

`Registry::spawn_with_resources(spec, ResourcePlan)` retains the real Child, image and non-clonable domain. Any resource error fails the launch. `observe_resources(instance)` brackets the kernel checks with two child observations. It compares `cgroup.procs`, `cgroup.threads` and two samples of `/proc/<pid>/task`, verifies every thread's CPU and memory-node constraints and rejects extra members or changed limits. Ordinary `spawn` cannot return a resource proof. An exited child does not release the entry's lease. The next acquisition must observe a genuinely empty group. Explicit owner unlock prevents a transient FD inherited across fork from extending the lease.

`memory.max` limits charged memory and can be exceeded transiently. Parent-created shared memory and the sealed ELF stay charged to the parent. Cpuset restricts allowed locations. Exclusive physical cores, locked pages and migration need independent setup.

## Applying projected launch fields

`HostConfig.projection_launch` binds a full projection object (up to 4 MiB), its `ObjectBinding`, cluster/namespace/host/process and a deployment-approved OS name map of up to 128 entries. The first-launch policy accepts registered active instances with role strategy, trust profile `qualified_sdk` and restart policy `never`.

Before startup App checks all local bootstrap channel identities, executable digest, process/strategy/host/namespace and role. The mapped UID/GID must equal the HostConfig and App's actual kernel credentials. The worker CPU set, NUMA node and memory budget must match the projection. The resource plan identifies the worker cgroup. After startup App compares the live kernel observation and image before exposing `LaunchBindingProof`. External workers are checked before returning their owner. For a local lazy worker, `prepare_start(now)` waits for live market data, starts the child and allows the resource check before the first intent. A failed proof reaps the managed child. Parameters and input scope, if enabled, share the projection identity and have separate gates.
