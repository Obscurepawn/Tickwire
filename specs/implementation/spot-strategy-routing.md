# Shared Cash Account Routing for Bybit and OKX Strategies

`AccountRunner` (`tickwire-spot-runner`) multiplexes `Submission` bundles—each carrying a `CanonicalCommand`, pre-assigned local `order_ids`, a send `deadline`, and a recovery dependency bundle—from a `Strategy` or `MultiStrategy` group into one shared Bybit or OKX cash spot account. A single `AccountRunner` owns the native `RestSession`, the `RecoveryQueue` shared with that session's local `Authority`, and an immutable content-addressed `Origins` index stored alongside the account's recovery files.

Sharing one single-writer `AccountGateway` across multiple logical strategies serializes competing claims on cash without cross-process locks while isolating per-strategy errors: a management permission refusal or insufficient-funds rejection returns a typed error to the originating strategy without stalling or freezing sibling strategies in the group.

## State Model and Origin Index

| Component | Key / Capacity | Contract |
| --- | --- | --- |
| `Origins<S>` | Scoped by `(risk_domain_id, venue, environment, account)`, `12,288` preallocated locator slots (`3 * MAX_ORDERS`) | Computes 32-byte SHA-256 locators on the stack with zero heap allocations (`ring::digest::Context`) and stores active aliases (including rotated `ModifyOrder.new_client_id` aliases bound via `bind_client_alias`) in a `WindowedTable<[u8; 32], Origin>` (`retention_window_ns` defaulting to `24 h`), retiring intents via `retire_intent` and lazily evicting expired aliases past `retention_window_ns` while enforcing strict conflict checks inside the active window. Backed by the configured `BlobStore` (`InMemoryBlobStore` zero-I/O default, `AsyncFileBlobStore` page-cache + async `fdatasync`, or `FileBlobStore`), falling back to `SelfDescribingClientId` decoding for cold-bootstrapped open orders. |
| `RestSession` / `AccountRunner` inflight | `1` request (single mode) or `inflight: BTreeMap<IntentKey, u64>` up to `MAX_ORDER_CONNECTIONS` (`16`) exclusive HTTP/1.1 slots (pooled mode) | Preserves single-flight execution when unpooled; when `RestSession::enable_connection_pool` is active, routes up to `16` concurrent intents across exclusive HTTP/1.1 slots via `OrderRouter` (8-sample warmup round-robin, microsecond EWMA + `9/8` hysteresis) and optional `VenueRateLimiter` (`Place`/`Modify`, `Cancel`, and `Query` isolated windows). |
| `Completion` & `StrategyRejection` | `{ logical_strategy_id, intent, response: Reply }` / `{ logical_strategy_id, intent, reason: TerminalReason }` | Correlates `RestSession::poll_tagged` responses by exact `IntentKey` (`poll` and `poll_all`) to the submitting strategy member, and surfaces non-freezing local admission/STP/modify/rate-limit refusals with exact `TerminalReason` classification (`drain_strategy_rejections`, `Error::terminal_reason`). |

Because a host crash or disk fault mid-registration can leave an immutable `Origins` alias written even if the subsequent WAL append never completed, management lookups (`Cancel`, `Query`) and private fill correlations (`record_fill`) treat `Origins` as an index only: the referenced `CanonicalCommand` must **also** exist in the authoritative `AccountJournal`.

## Submit and observe

1. **Bind origin identities or verify target lineage**: For a new spot order, `AccountRunner` registers one local order ID and one native `ClientId` against `(intent_exec_epoch, intent_id, command_digest)` within the account's `Scope`. For a `Modify`, `Cancel`, or `Query`, it resolves the original admitted `CanonicalCommand` through that binding (using the active `ClientId` or any rotated `ModifyOrder.new_client_id` alias registered via `Origins::bind_client_alias`) and checks instrument and `ClientId` equality; if the caller also supplies a native venue order ID, the `Account` reducer must already have bound that native ID to the target order.
2. **Precheck slot/quota availability, stage recovery closure, serialize shared cash, and isolate peer refusals**: Before staging `Origins` or `RecoveryQueue`, `AccountRunner` runs `RestSession::precheck_submit` so a full pool (`Error::Busy`) or local `VenueRateLimiter` rejection (`SessionError::RateLimited`) returns immediately with zero `Account` balance hold or `AccountJournal` append—keeping `Cancel` (`20/1s` Bybit, `60/2s` OKX symbol) and `Query` (`50/1s` Bybit, `20/2s` OKX) windows completely isolated when `ORDER` caps fill, and debiting `Place`/`Modify` tokens only **after** `AccountGateway` admission succeeds so local `CrossesBook`, `InsufficientAsset`, `TooManyPendingActions`, or `NoChange` refusals burn zero tokens. Once prechecked, `AccountRunner` stages the recovery bundle under `command_digest` on `RecoveryQueue`. `AccountGateway` evaluates the shared balance and optional `StpBook` (`set_stp_enforcement`), reserves cash or modification exposure delta once, synchronizes the recovery closure and `Admit` record to the configured `StorageMode`, and re-evaluates the live `Gate` immediately before the first plaintext byte enters TLS—ensuring the next strategy polled immediately observes the prior strategy's reservation even while earlier intents are still in flight on sibling HTTP/1.1 slots. On `Modify`, `Cancel`, or `Query`, `Account` checks the target order's current `logical_strategy_id`, manager `(instance_id, generation)`, and `owner_revision`: a mismatch returns `Error::ManagementDenied` to the submitting strategy via `on_submission` without appending an admission or transmitting a request, while `AccountRunner` continues polling peer queues. Likewise, when an unfrozen `Account` or `RestSession` rejects a command with `CrossesBook`, `OrderNotOpen`, `UnknownOrder`, `TooManyPendingActions`, `InvalidPrice`, `InvalidQuantity`, `NoChange`, `InsufficientAsset`, `InsufficientCapital`, `Limit`, or `SessionError::RateLimited`, only the originating member receives the typed refusal alongside a classified `StrategyRejection` (`TerminalReason` via `drain_strategy_rejections`), never calling `stop_sending()` or stalling peer queues.
3. **Deliver tagged native replies, project cumulative fills, and journal economic fills separately**: Immediate submission outcomes return synchronously via `Strategy::on_submission`. As HTTP responses decode across one or more slots (`poll` or `poll_all` via `RestSession::poll_tagged`), `AccountRunner` removes `intent` from `inflight`, records native order IDs on `Reply::Acknowledged` and `VenueEventBody::Modified` / `VenueEventBody::ModifyRejected` on synchronous `Modify` replies, enqueues per-order `QueryDesk` asks (`AskKind::Order` or `AskKind::Amend` under `DoubtReason::AmendAmbiguous`) on `Reply::Unknown` or ambiguous `Reply::RequestIssue`, and routes each completion to the originating `logical_strategy_id` via `on_request_reply` (requiring exact `(instance_id, generation)` equality whenever tracked by `MultiStrategy`). When `AccountRunner::set_projected_fill(true)` is enabled, advancing cumulative filled quantities on Bybit `order.spot` (`cumExecQty`, `cumExecValue`, `avgPrice`) and OKX `orders` (`accFillSz`, `avgPx`) invoke `AccountGateway::on_cum_qty` to emit volatile `ProjectedFill` items (`drain_projected_fills`) ahead of trade execution frames, and terminal venue updates classify exact `TerminalReason` values (`order_terminal_reason`). Neither a new-order acknowledgement nor a cancel acknowledgement releases reserved cash; settled balance and fee updates derive strictly from durable `AccountJournal` events, including verified private trades passed to `record_fill`.

## Core Invariants and Failure Semantics

* **Idempotent retries vs. sender-halting conflicts**: Re-submitting a byte-identical admitted intent returns its recorded gateway `Status`; any conflicting origin alias or altered command payload under an existing intent halts the sender.
* **Clock monotonicity guard**: `AccountRunner` checks `LocalTime` monotonicity and `ClockDomain` continuity before every strategy poll and submission; a zero timestamp, domain change, or backward reading immediately calls `stop_sending()` and returns `Error::Clock`.
* **Uncertain sends retain reservations**: Ambiguous transport failures after partial byte acceptance leave reserved funds locked, whereas proven zero-byte aborts synchronize `RecoveryRecord::Aborted` in `AccountJournal` before releasing cash.

## Local Loopback Paper Exchange

Run the self-contained paper workflow against a fresh state directory per invocation:

```sh
cargo run --locked -p tickwire-spot-runner -- paper bybit /tmp/tickwire-bybit-paper-1
cargo run --locked -p tickwire-spot-runner -- paper okx /tmp/tickwire-okx-paper-1
```

In each run, two short-lived strategy processes read a synthetic BTC quote (`ask = 60,000 USDT`) and emit a `0.001 BTC` limit buy if the ask is within threshold (`60,000` for logical member `8` and `60,001` for logical member `9`), writing canonical commands, decision inputs, and descriptors into separate file queues. `MultiStrategy` drains both queues while the parent process pre-approves the two expected command digests in `Environment::Test`, opens a file-backed `AccountGateway`, and transmits signed native requests to a loopback TLS peer (`paper_peer.rs`) that verifies HMAC signatures and `ClientId`s before returning acknowledgements (delivered to the file-queue readers after the short-lived producer processes have exited).

The run completes with two native acknowledgements, two open orders, and `120 USDT` reserved; re-running against the same state directory fails cleanly (`AlreadyExists`). Production `live` deployments execute the identical `AccountRunner` state machine backed by a durable private WebSocket reader, bracketed REST scans, and supervisor grants as documented in [Run an account](spot-execution.md#run-an-account).

## Performance and Cost

Under the file-queue intake profile, startup pays child-process spawn overhead and a local TLS handshake. Each submitted decision writes worker input and dependency files; intake parses the queue descriptor, hashes and reads those files, copies `CanonicalCommand`, and synchronizes one `Origins` content object plus three scoped alias files before entering `AccountGateway` (which signs and encodes the HTTP payload, `fsync`s recovery dependencies and the WAL, and samples the `Gate` before the first TLS byte). Because each `RestSession` holds one in-flight HTTP slot, a slow venue reply delays subsequent outbound commands on that session. These costs are derived structurally from the control flow rather than measured as latency percentiles.

## Verification and References

```sh
cargo test --locked -p tickwire-spot-runner --all-targets
```

Boundary tests verify that against an `80 USDT` balance and two competing `60 USDT` buy orders, the first strategy receives a native acknowledgement, the second receives an `InsufficientAsset` refusal, and `20 USDT` remains available; a separate first-byte test revokes the action grant prior to plaintext transmission and confirms zero bytes reached the TLS peer while the reservation released cleanly.
