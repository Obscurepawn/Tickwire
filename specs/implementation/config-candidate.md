# Configuration candidates, projections and pure plans

`tickwire-config` turns TOML or JSON into one content-addressed configuration value. Pure checks can establish what the bytes request, whom a change affects and which resources it would need. The service binds these results to committed state, sources and actual running processes. [Configuration crate](../../crates/tickwire-config/src/lib.rs) · [Service planning](config-planning.md)

## Parsing and static validation

The hard input limit is 16 MiB and 64 container levels, with a default depth of 32 and at most 262,144 value nodes. Strategy parameters permit 16 levels. Duplicate JSON keys, including escaped equivalents, are rejected during construction. Floats, integers outside ±(2⁵³−1), TOML dates and invalid encodings fail. Integer −0 canonicalizes to 0. Float syntax such as `-0e0` fails. Arrays retain order, and object keys use RFC 8785 UTF-16 ordering before SHA-256.

`validate_structural()` uses the pinned Draft 2020-12 schema and format checks with no external retrieval. `normalized_configuration()` explicitly adds the sole default `RoleBinding.cluster_scope=false`, rechecks the budget and computes a new hash. Generic parse preserves the original value. Static validation checks IDs, references, roles, instances, risk budget assets and amounts, CPU conflicts, memory, primary/standby and three-voter failure domains, ring/arena geometry, shared-memory budgets and deadline ordering. Byte arithmetic is checked. Decimal budgets are compared exactly. OS CPU and NUMA IDs need not be contiguous. Actual presence is checked against host inventory. [System schema](../contracts/system-config.schema.json)

The artifact catalog validates full references and raw SHA-256, with up to 4,096 objects, 16 MiB each and 512 MiB total. An exact retry reuses its allocation. Dependency scanning records JSON Pointer use sites and lists credential references separately. Parameter schemas are capped at 1 MiB and 32 levels, allow only same-document references and use a linear regex engine with 1 MiB each for compiled and DFA caches. Validation binds strategy parameter and schema hashes. It leaves free-form strategy parameters classified Quiesce. [Artifact checks](../../crates/tickwire-config/src/artifacts.rs)

## Delivery and capacity

`PinnedPolicy::decode` verifies the strict policy document and its whole-file digest. Each process gets only approved accounts, venues, topics and explicitly assigned credential uses within the role's built-in ceiling. A strategy gets no credential purpose. A `secret://` reference smuggled in a parameter value still fails unless authorized. The global digest and permission-filtered payload digest are separate.

`ProjectionSet` requires an exact policy target for every process. `ProjectionDelivery` covers the union of old and new IDs and labels each Added, Retired, Changed or RevisionOnly. Even an unchanged payload and policy must receive the next global revision. The caller cannot shrink this set. All payloads together are bounded at 4,096 targets and 512 MiB, separate from runtime memory for coexistence. A `ProjectionObject` validates the whole object's hash, target, global revision/hash, policy revision and recomputed payload hash. Revisions range from 1 through 2⁶³−1. The object must fit both 4 MiB and the configured delivery limit. Retirement retains the old permission payload and policy while binding the new global hash. The plan specifies the retirement action. [Projection objects](../../crates/tickwire-config/src/projection_object.rs)

`CapacityAssessment` binds the complete host inventory and retained resource snapshot. It checks host/failure domains, OS CPU-to-NUMA and socket/core mapping, reserved memory, SHM limits and additional CPU/shared/private memory responsibilities. A hot loop and housekeeping may not occupy the same physical core. Supervisor is assigned housekeeping capacity. The result records the candidate, inventory and retained-snapshot digests. The service must still establish source freshness and the current registry head.

`ProjectionFile` renders a process-specific TOML payload and separate materialization metadata. It verifies version, target, payload and policy against the delivery object. Desired uses apply position zero. Effective requires a nonzero boot and apply position. Operation and slot must be nonzero UUIDs. A file can be up to 8 MiB. The final file digest lives in its receipt. Recovery also verifies strict TOML and its full metadata against the expected bytes. [Materializer](config-materializer.md)

## Change actions and authority

`ChangeSet::between` classifies full structural paths. It aligns entities by stable IDs and treats relative reordering as its own change. Risk-budget tightening may be Hot. Relaxed protections require a quiescent boundary and both operator and risk-admin permissions in the affected account scope. An operator for account A and risk-admin for account B cannot approve a relaxation on A. Adding budgets, adding/removing strategies, contract overrides and changes to tradable symbols likewise require the proper risk authorization. Increasing disk-warning/freeze percentages or a receive window relaxes a protection. A policy with no account consumers requires cluster authority. Strategy-owned fields remain Quiesce regardless of their names.

`ComputedPlan::compute(base_revision, base, prepared, delivery, options)` checks all base/candidate/delivery identities and fixes the base revision/hash/ETag, successor revision, options, candidate and per-target actions. A plan fits 1 MiB and has its own domain-separated digest. Defaults are a RollingRestart ceiling, RejectIfExceeded exposure policy and no target hints. A valid hint cannot remove targets. Unknown hints, an action above the ceiling, ForbiddenRuntime and unclassifiable projected changes all fail.

A target receives its greatest relevant action across both old and new dependencies. A private strategy change affects that strategy. Account, risk and topic changes also reach the responsible execution, protection and publication/consumption targets. An unrelated publisher does not inherit an account-only risk change. Process changes also reach the host supervisor and its dependent accounts/topics. Generic IPC geometry, control, replication and qualification changes reach everyone. Journal, local files, timeouts and observability follow their actual projection dependencies. Byte-identical payloads can still require action. Each row carries old/new projection hashes, policy revisions, locations, affected accounts and paths, and the outstanding requirements for exposure, quiescence, retirement, succession, directory or credential transfer.

`EncodedPlan::decode` checks the canonical JSON, exact digest, ordered unique arrays, ETag, consecutive revisions, action and projection sides. `ComputedPlan::verify_encoded` recomputes from the supplied complete base, preparation and delivery and compares byte for byte. A recomputed hash alone cannot bless a changed action or missing target. `plan::rules_digest()` separately hashes a framed, compile-time list of planner, classifier, dependencies, strict codec, schemas, Cargo inputs, lockfile, build configuration and toolchain. The archive stores it outside the plan encoding. The pure planner reads neither the clock nor runtime authority.
